# Runtime Follow-ups

ADR-0024 defines more than the first `doctor`, `settings`, consensus, and context scaffold PRs. This file keeps the deferred surfaces explicit so runtime operator commands do not grow into hidden workflow, host-native config, context mutation, or plugin-install mutation by accident.

## Deferred to follow-up PRs

- Plugin management beyond the explicit settings executor: `runtime:settings --execute-plugin-management` can run allowlisted host-native plugin install/update/add/upgrade commands and persist sanitized execution artifacts, `runtime:settings --apply-codex-plugin-hooks` can perform the narrow Codex user config write for `[features].plugin_hooks = true`, and `runtime:settings --attest-codex-hook-review` can record the operator's completed `/hooks` review/trust step as an artifact; broader host-native config apply, Codex trust-state mutation, plugin uninstall, authentication automation, sandbox/permission changes, richer retry policy, and deeper retention/cancellation policy remain follow-up scope.
- Consensus executor depth beyond the explicit boundary: `runtime:consensus execute --execute` can dispatch allowlisted companion peers, store raw stdout as artifacts, maintain per-peer progress metadata, classify permission/sandbox/auth preconditions as `operator_action_required`, classify sanitized failure/retry metadata with bounded timeout remediation, and expose advisory `execution_remediation` blocks with retry commands, proof commands, suggested timeout increases, and artifact pointers. It can also plan broad manual/subagent rosters without a hidden fixed peer-count cap. Follow-up scope remains richer cancellation, deeper peer smoke matrices, automated synthesis, and risk/budget-driven peer selection policy.
- Worktree execution beyond read-only planning: `runtime:worktree plan` can inspect current git/worktree state and suggest commands, but branch creation, `git worktree add/remove/prune`, checkout switching, commit, push, and PR creation remain explicit operator actions outside runtime.
- Context automation beyond read-only checks: automatic capture triggers beyond the current `runtime:context` scaffold and explicit budget check. No automatic host switch, new workflow start, or host-session compaction.
- Completion footer command-surface integration beyond latest context lookup, handoff guidance, PR handling readiness, and completion-state rendering: the helper remains advisory and pointer-only, can read the latest existing `runtime:context` artifact with stale/source metadata plus guidance, can render PR handling readiness, and can emit a conservative completion-state enum plus state-derived next action. Later PRs may add richer command-surface integration, but must still avoid automatic context mutation, automatic session start, raw peer/consensus output in the main session, or automatic commit/push/PR mutation.
- Deep peer smoke evidence beyond the bounded `runtime:doctor` executor: current doctor output includes a plan-only `--deep-peer-smoke` preflight, an explicit `--execute-deep-peer-smoke` companion-contract executor that omits raw peer stdout, and direction-level execution readiness in the readiness matrix. Permission, sandbox, and child-process auth blocks are operator preconditions rather than runtime implementation failures. Cancellation or multi-round smoke policy remains follow-up scope.
- Permission proof evidence beyond the bounded `runtime:doctor` executor: current doctor output includes `--permission-proof` plan-only preflight, an explicit `--permission-proof --execute-permission-proof` companion-contract executor under host-native permission defaults, and direction-level execution readiness in the readiness matrix. Operator preconditions are surfaced as `operator_action_required` with `permission_required`, `sandbox_blocked`, or `auth_required` kinds. Cancellation, multi-operation permission matrices, or any settings-driven sandbox/approval changes remain follow-up scope. Settings must not silently relax sandbox or approval policy.
- Runtime artifact retention beyond read-only inventory: `runtime:doctor --artifact-inventory` reports generated `.agentic-plugins/runs` counts, bytes, age metadata, and retention pressure without reading raw artifact bodies. Artifact deletion/compaction remains follow-up scope and must stay behind a separate explicit boundary if added later.
- Codex capability drift beyond the current baseline: [`codex-capability-baseline.md`](codex-capability-baseline.md) records official Codex docs plus local CLI `0.130.0` observations for skills, plugins, marketplaces, MCP, subagents, hooks, config, sandboxing, and approvals. `runtime:compat snapshot/check/ingest-release-notes/plan` can now record host-version drift and content-backed release-note planning artifacts, but future plugin-hook integration beyond explicit `plugin_hooks` enablement, broader host-native Codex config writes, MCP mutation, or non-marketplace plugin management must refresh that baseline first.
- Claude-vs-Codex parity drift beyond the current baseline: [`host-parity-baseline.md`](host-parity-baseline.md) records official host docs plus local Claude Code `2.1.143` and Codex CLI `0.130.0` observations for plugin command shape, hooks, subagents, agent-team/team-mode semantics, model/effort, settings roots, permission boundaries, worktrees, memory roots, and `.agentic-plugins` ownership. `runtime:compat` can create compatibility update plans from explicit release-note artifacts, but future team-mode, plugin-hook, host-native config, automatic subagent fanout, or host-root migration work must refresh that baseline first.
- Runtime compatibility depth beyond the first `runtime:compat` scaffold: current compat can snapshot local versions, compare against remembered baseline versions, store explicit release-note files, store URL pointers, explicitly fetch URL content with `--fetch-release-notes-url`, emit advisory update plans, and expose latest compat metadata through `runtime:doctor`; `runtime:cutover` can aggregate the latest compat evidence into the read-only scorecard audit. Follow-up scope remains automated baseline freshness warnings, richer release-note parsing, and stricter content-backed release-note scoring.
- Release/install continuity beyond the current plugin-management dry-run and executor: every release-managed runtime/engineer/orchestrator slice should continue through feature PR, release-please PR, marketplace/version validation, explicit installed-plugin refresh, doctor/settings verification, branch cleanup, and next-slice restart from updated main plus updated installed plugins. Runtime may report and execute allowlisted update commands, but must not silently mutate host plugin installs or declare release completion before installed-state evidence is recorded.

## Boundaries

- `plugins/companions` remains a script-only library plugin.
- Runtime owns cross-plugin host/runtime truth; it does not become an engineer or orchestrator command bundle.
- Codex plugin-hook feature/trust state and permission limits must stay visible in output instead of being treated as host parity.
- Codex marketplace-only plugin management and disabled local `plugin_hooks` must stay visible until official docs and local CLI evidence both support a broader runtime path.
- Claude agent teams must not be treated as the portable cross-host team-mode substrate. A portable team-mode design should stay artifacted through runtime/orchestrator consensus, explicit companion dispatch, manual/subagent lanes, and worktree planning unless both hosts expose a compatible team primitive.
- Consensus execution must stay bounded by explicit `--execute`, max rounds, max peers, process budget, and timeout caps. Runtime must not add automatic unbounded loops or relax host permissions.
- Worktree planning must remain read-only unless a future PR adds a separate explicit execution boundary with dry-run defaults.
