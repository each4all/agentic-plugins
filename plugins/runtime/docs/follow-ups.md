- ADR-0035 §4 active-execution boundary guard — **first slice shipped**: the registry + static test live at `tests/plugin-shape/runtime-executor-registry.mjs`, `runtime-executor-scan.mjs`, and `test-runtime-executor-guard.mjs` (zero-dependency token-aware scan with a comment-stripping/regex-aware tokenizer — not acorn/AST and not a raw grep; `test:` scope, no runtime bump). The hard gate is **runtime-only** (`plugins/runtime/scripts/**/*.mjs`). It is **structurally fail-closed**: a new capability-module import (named/namespace/aliased/dynamic-non-literal/re-export), a process/network primitive, a non-allowlisted or non-literal ("arbitrary") command, or a non-literal argv outside the registry fails the conformance test — including via wrapper aliasing (`const r = runCommand`), namespace member calls (`cp.spawn`/`doctor.runCommand`), and exact-match forwarding exemptions. On top of that structural floor it enforces the §4 ceiling for the shipped surface — `shell:true`/computed/truthy shell option, `sh -c`, dangerous argv verbs via a **per-host-CLI positive verb-path allowlist** (auth bare `login`, `--sandbox`/`danger-full-access`, `hooks trust`, session `resume`/`fork`/`compact`, destructive `remove`/`prune`; `login status` etc. stay allowed), the single permitted retired-plugin `uninstall …@agentic-plugins` template, network GET-only in compat, and external-process kill (only doctor's exact own-child `child.kill('SIGTERM')`, plus the registered signal-0 liveness probes in `ALLOWED_PID_LIVENESS_SITES` — `process.kill(pid, 0)` sends no signal and is POSIX's existence check, form-pinned to a literal `0` so a variable or any real signal in the same file still fails; today the sole entry is `bootstrap-artifacts.mjs` stale-lock reclaim, which machine-bootstrap-contract.md §13 fixes as the staleness rule). **A new mutating executor (e.g. follow-up C) MUST add its capability import / command / argv verb-path to the registry, or the conformance test fails — the mechanical half of the ADR-0035 §5 add-gate.** Known v1 limitations (covered by the §5 human review, not silently safe): the argv allowlist is **verb-level, not per-call-site** — a new file reusing an already-allowed safe verb (`git init`, `rev-parse`) is not flagged; exotic indirect dispatch (computed-member `obj[name](…)`, deep object indirection) beyond the closed alias/namespace/destructuring/reassignment forms is out of scope; the kill-gate is **receiver-name + signal** (`child.kill('SIGTERM')`), not bound to the exact `runCommand` spawn, so a different `child`-named SIGTERM kill inside the kill-site file would pass; forwarding/projection exemptions are **shape + clean-literal-resolution** heuristics, not full scope analysis; a dynamic/computed shell key via a variable (`const k='shell'; {[k]:true}`) and a regex literal immediately after a brace-less control-flow condition (`if (x) /re/;`) are tokenizer/resolution edges (runtime uses braces and literal keys throughout). - Permission-advisor safety grade vs. wildcard generalization (ADR-0038): the advisor grades each **observed** command, but `generalizeCommand` then collapses distinct commands into one wildcard — `node safe.mjs` (graded `allow`) and `node -e '<arbitrary>'` (graded `ask`) both become `node *`. If only the safe observation exists, the plan recommends `Bash(node *)` into `allow`, and under prefix semantics that pattern also covers the unsafe sibling. So a recommended `allow` rule can be **broader than the one safe command that produced it**. Surfaced by the Refine-verify peer on the S1 discoverability slice (`refine-verify-20260714T062015Z-1a4d7e`). This is **not** a patch — it is a policy decision under ADR-0038: refuse to emit a pattern whose observed family contains an unsafe member? grade the *pattern* rather than the instance? narrow the wildcard (`node * ` → `node <subcommand> *`) where the family allows? Until it is decided, `commands/settings.md` and `skills/settings/SKILL.md` state the caveat plainly and tell the operator to review the fragment before applying it. Adjacent, and cheaper: `--permission-plan-max-files` / `--permission-plan-max-file-bytes` parse through `Number.parseInt`, which accepts `12junk` as `12` and `2e3` as `2` — a strict parse should reject rather than silently coerce.
- Permission-advisor **grader vs. pattern-emitter divergence on a path-shaped program** (ADR-0038). `gradeCommand` classifies the program token as written; `generalizeCommand` **basenames** it (`basenameProgram`, added to keep a private path out of the emitted rule). So `/usr/bin/npm test` grades `ask` (program `/usr/bin/npm` is unrecognized) while the pattern it emits is `Bash(npm test)` — the grade and the pattern describe **different programs**. The direction is conservative today (a path-shaped invocation of a safe program is merely over-asked), which is why this slice did not touch it. It is **not** obviously fixable by making the grader basename too: `/tmp/evil/npm test` would then grade `allow`, and the emitted `Bash(npm test)` would not even match the observed command in the host — so the naive unification produces a rule that is both wrong and useless. The real question is whether a path-qualified program should be **generalized at all** or dropped as an observation, which is a policy decision alongside the wildcard-collapse row above. ## Boundaries

- `plugins/companions` remains a script-only library plugin.
- Runtime owns cross-plugin host/runtime truth; it does not become an engineer or orchestrator command bundle.
- Codex plugin-hook feature/trust state and permission limits must stay visible in output instead of being treated as host parity.
- Codex plugin-management command shape and the removed `plugin_hooks` flag (plugin hooks now follow plugin enablement) must stay visible in output as host truth, not collapsed into Claude parity. Codex `0.137.0` per-plugin `add`/`list`/`remove` is recognized (ADR-0032) as the `per-plugin-and-marketplace` surface; output must claim neither a marketplace-only limitation (on `0.137.0`+) nor full Claude parity (`update`/`enable`/`disable`/`details`/`validate`/`prune` remain absent).
- Claude agent teams must not be treated as the portable cross-host team-mode substrate. A portable team-mode design should stay artifacted through runtime/orchestrator consensus, explicit companion dispatch, manual/subagent lanes, and worktree planning unless both hosts expose a compatible team primitive.
- Consensus execution must stay bounded by explicit `--execute`, max rounds, max peers, process budget, and timeout caps. Runtime must not add automatic unbounded loops or relax host permissions.
- Worktree planning must remain read-only unless a future PR adds a separate explicit execution boundary with dry-run defaults.
