## Context

### What the owner decided

| id | decision (2026-10-07 UTC) |
|----|----|
| L1 | Each lane is its own branch, cut from `origin/<baseline>`, with its own pull request. Successors wait for their predecessor to land: [ADR-0062](0062-subtask-completion-recorded-at-landing.md) and ADR-0063 D3a are unchanged. At commit the driver runs a read-only overlap check. ### What the macro's Plan-verify found

Codex run `macro-plan-20261007T174903Z-6a7daab` (verdict concerns) found
that:
- storage, the git checkout and pointers are three separate contracts;
- the explicit resolvers and engineer scans need the root as much as
  `statePaths` does;
- B′ must be threaded end to end;
- a macro already living in a linked worktree's own state needs an operator
  cutover, with a release checkpoint;
- overlap must be checked pairwise, and the landing report must survive a
  restart;
- the consensus proposal needs executable state, not prose;
- locks, budgets and the throttle have edges under concurrency.

Each is decided below.

## Decision

### Decision 1. Three contracts: where state is stored, where git runs, how pointers resolve

**(a) Storage: the state root and the read set.**
- **The default state root** of a checkout is
  `dirname(git -C <checkout> rev-parse --path-format=absolute --git-common-dir)`
  when that directory is named `.git`, and otherwise (a git dir under
  another name, as a bare repository's usually is) the checkout's toplevel.
  It is where git places the main worktree, the rule `ledger.mjs:38-48`
  already applies to the macro lock. For a repository without linked
  worktrees whose `.git` is a directory, it equals the checkout.
  - **It is the main checkout only when that checkout's `.git` is the
    common dir itself.** A main checkout whose `.git` is a file pointing
    elsewhere (`git init --separate-git-dir <d>/.git`, or the same `git
    clone` option) leaves `<d>` as the default state root: a directory that
    holds the git dir and no checkout. Measured 2026-10-08 on git 2.54 in a
    scratch repository: from a linked worktree the common dir is `<d>/.git`,
    and `git worktree list --porcelain` names `<d>` as the main worktree and
    omits the real checkout; in `<d>`, `git rev-parse --show-toplevel`
    answers `<d>`, with the same common dir, and `git ls-files --deleted`
    lists every tracked file. Git records where each linked worktree is
    (`<common dir>/worktrees/<name>/gitdir`) but not where the main one is,
    so nothing git records tells `<d>` from a real main checkout. A look at
    its files catches the plain case, but it is no proof: a `<d>` that also
    holds a file named as a tracked one passes it (measured by this ADR's
    review, git 2.54).
  - **The operator attests the main checkout, once.** The cutover runbook
    has the operator run `state.mjs shared-creation --enable` (below) in the
    main checkout; that run is the attestation that the directory is the
    repository's main checkout. The command checks for the mistakes it can
    see, and refuses unless, there:
    1. the git dir is the common dir, and it is named `.git` (it is the main
       worktree of a repository whose worktrees share a root);
    2. the toplevel is the default state root, which also refuses a `.git`
       that is a file pointing elsewhere;
    3. as a sanity check, an index entry that is checked out (`git ls-files
       -t` tags it `H`; a skip-worktree entry, `S`, is not) is present on
       disk. An index with no such entry refuses.

    The real main checkout of a separate-git-dir layout fails the second
    test, and its `<d>`, run there by mistake, the third (with a sparse
    checkout too, whose `S` entries are not counted). A bare repository has
    no checkout to pass them. Passing them is the operator's attestation
    checked for plain mistakes, not a proof. Lanes require the switch
    (Decision 2), so a repository whose main checkout is not attested has
    no shared root: lanes are refused (Decision 5), and records are created
    per checkout, as today.
  - **Until then, no command run in another checkout creates a record or
    takes a creation lock under the default state root.** While the switch
    is off, creation and archive take only their own home's locks
    (Decision 2). A command writes there only records it found there (the
    main checkout's own, which a linked worktree's writers update and its
    children write back to; none in a separate-git-dir layout) and the
    driver's files kept under the main worktree (below), which every
    checkout locates alike and which need it writable, as the macro lock
    does today (`mainWorktreeRoot`, `ledger.mjs:38-48`, the same rule). So a
    `<d>` that cannot be written leaves the personas and orchestrator
    working as today. In a separate-git-dir layout the scans of every other
    worktree (Decision 2) miss the real main checkout's homes, which `git
    worktree list` omits; with creation per checkout, that is today's
    behaviour.
- **`stateRoot(checkout)`**, where new shared records are *created*,
  depends on the repository's shared-creation switch:
  - **off** (absent: the state until the cutover): the checkout's toplevel,
    as today. A record is created only where every host's readers in that
    checkout already look, whatever their version;
  - **on**: `AGENTIC_STATE_BASE` when set (Decision 2), else the default
    state root. A dispatched child is the exception: it is created beside its
    macro (Decision 3).
- **The shared-creation switch** is one file per repository,
  `.agentic-plugins/state/shared-creation.json` under the default state root
  (ignored with the rest of `state/`). The cutover writes it (Decision 4,
  item 4) with `state.mjs shared-creation --enable`, which SR adds to the
  persona and orchestrator scripts, run in the main checkout once the
  release tuple is verified on both hosts, as the operator's attestation of
  the main checkout (above); it records when, and the versions
  verified, and later the driver's first lane creation (Decision 4,
  item 4, Rollback). Only the rollback
  turns it off. A switch file that cannot be read or parsed refuses every
  creation, with a diagnostic, rather than guess. An older script never reads
  it: that is why it is turned on only once no older script runs.
- **The read set**, where existing records are *found*, is the default state
  root and the checkout's toplevel: one location when they coincide. Every
  reader, lookup and scan searches it, whatever `AGENTIC_STATE_BASE` or the
  switch says. The variable and the switch choose where a record is created,
  never where it is found, so two sessions of one checkout, one with the
  variable and one without, see the same records.
- **Shared:** the workflow records of the persona and orchestrator homes,
  `.agentic-plugins/state/<engineer|founder|designer|orchestrator>/`:
  `workflows/`, `archive/`, `peer-runs/` and `consensus/` (Decision 8), and
  the same directories of the legacy homes, which only engineer and
  orchestrator have (`.claude/agentic-engineer/`,
  `.claude/agentic-orchestrator/`).
  - One active workflow per branch (ADR-0018 §sub-2) now holds across the
    read set, and at creation across the repository (Decision 2; before the
    switch is on, the check narrows a race it does not close). For a
    persona workflow, keyed by the branch its checkout has out, git mostly
    holds it already: by default it checks a branch out in one worktree only
    (`--force` and `--ignore-other-worktrees` override that). A macro is
    keyed by its `git_baseline.branch`, the integration branch, which the
    checkout holding the macro need not have out. So there is **one active
    macro per integration branch per repository**: two macros on `main` can
    no longer run side by side from two checkouts, as two homes allow today.
    Lanes are how one macro runs work in parallel. A refusal names the
    worktree and the file that hold the other workflow.
- **Per checkout (W9):**
  - runtime-owned state, `.agentic-plugins/state/runtime/` (the session
    capture, `plugins/runtime/scripts/lib/session-capture-inspect.mjs:19-31`):
    "this checkout's last turn";
  - each home's `last-session-handoff.json` and its `.footer-rendered`
    markers: the last terminal handoff in this checkout, which its own
    SessionStart and Stop read. Shared, two lanes would overwrite each other,
    and attention's Stop relay (`readFreshProjection`,
    `plugins/attention/scripts/lib/sensor.mjs:224`, called from
    `plugins/attention/adapters/claude/hooks/stop.mjs:54`) in one session
    would report another session's completion. The sidecar writes the slot in the
    checkout its command runs in;
  - `.agentic-plugins/runs/`, `tmp/` and `cache/` (doctor, settings,
    consensus and autopilot run ledgers).
  - The exceptions live under the main worktree: in
    `.agentic-plugins/runs/autopilot/`, the macro lock, as today, the
    landing log (Decision 7), the lane removal intents (Decision 5) and the
    open-run records (Decision 6); in
    `.agentic-plugins/runs/cutover/`, the cutover manifests (Decision 4,
    item 4).

**(b) Git: the checkout.**
- Every git fact comes from a checkout, never from the state root: branch,
  HEAD, porcelain, `status_digest`, the clean check, commits. Runbooks keep
  `REPO_ROOT="$(git rev-parse --show-toplevel)"` for git and resolve storage
  from it with `stateRoot()`. A CLI that takes `--repo-root` keeps reading it
  as the checkout, and the `repo_root` a record stores at create names the
  checkout that created it. It says where a record was created, never where
  it lives: no script reads it to find the file
  (`plugins/orchestrator/scripts/state.mjs:3178-3180`), and a record moved
  since, by hand or by the cutover, keeps it. This macro, moved by hand into
  the autopilot home worktree, records the main checkout.
- Facts about a workflow whose branch the caller is not on (a path-targeted
  terminal write, a Stop sweep) come from git's shared refs and from the
  worktree that holds the branch:
  - tip and subject from `refs/heads/<branch>`, which every worktree of the
    repository shares;
  - working-tree facts only from the worktree that has the branch checked out
    (`git worktree list --porcelain`), and "unavailable" when none has.
  - The sidecar's HEAD probe of an inferred root is replaced by this rule.
    `inferStorageFromWorkflowPath` yields the home and the state root, never
    a checkout.
- **Stop and sweep.** A Stop acts on its own checkout's branch, as today. The
  branch-agnostic sweep (`persona-pipeline/files/scripts/stop-archive.mjs:322-387`)
  leaves alone every workflow whose branch is checked out in *any* worktree:
  only that worktree's Stop sees its working tree. Today's rule (`:346`,
  "the per-branch path owns it") covers only the sweeping checkout's branch.
- The macro's lifecycle scans for its children read the read set and the
  own homes of every other worktree (`git worktree list --porcelain`), as
  creation does (Decision 2): the archive guard's scan of engineer children
  (`plugins/orchestrator/scripts/state.mjs:4381-4388`, gate A4 at
  `plugins/orchestrator/scripts/stop-archive.mjs:96-101`) and the detach
  passes of `/orchestrator:finalize` and `/orchestrator:abort`
  (`plugins/orchestrator/commands/finalize.md:136-176`,
  `plugins/orchestrator/commands/abort.md:134-138`). A child that an
  older persona left in a checkout's own home therefore still blocks the
  archive or is detached, instead of being missed.

**(c) Pointers.**
- A pointer into a shared record is written relative to the state root,
  spelled as today: `.agentic-plugins/state/<plugin>/<dir>/…` or
  `.claude/agentic-<plugin>/<dir>/…`, where `<dir>` is `workflows`,
  `archive`, `peer-runs` or `consensus`.
- A consumer resolves a pointer with one of those prefixes the way the
  readers find records: in its own checkout's read set (Decision 1(a)), the
  default state root first, then the toplevel, the first that exists. A
  workflow kept in a checkout's own home, during the rollout or under
  `AGENTIC_STATE_BASE`, is therefore still reached. A record found under both
  is the ambiguity Decision 4 refuses, never a choice.
- Every other pointer (a home's handoff slot, runtime state, `runs/`)
  resolves against the consumer's checkout's toplevel, as today.
- No pointer spells `..` or an absolute path, so the arbiter's hardening
  (`entry-brief-arbiter.mjs:67`) stays as it is. Every stored pointer keeps
  its meaning, because today the state root is the toplevel.
- The driver renders its halt and landing pointers by the same rule. Today
  `observe.mjs:52-55` falls back to an absolute path outside the checkout.
  The files the driver keeps under the main worktree (the macro lock, the
  landing log, the lane removal intents, the open-run records) are never
  stored as pointers: the
  driver and its CLI reach
  them through `mainWorktreeRoot`, and print them as absolute paths in the
  terminal only.

### Decision 2. The override variable: `AGENTIC_STATE_BASE`

- **Not `AGENTIC_STATE_ROOT`.** `_ROOT` names a plugin root. session-env
  would scrub a state override as a plugin root, so a test would lose it by
  accident, not by rule. A future persona named `state` would get the same
  name from the pipeline (§Context).
- **Value:** an absolute path, at the level of a checkout's toplevel, and one
  of exactly two: the default state root, or the toplevel of the checkout the
  command runs in. While the shared-creation switch is off, only the second:
  the default state root named from a linked worktree would create where an
  older host in that worktree does not look (Decision 4, item 3). Anything
  else (another worktree's toplevel, a directory outside the repository)
  fails closed, with a diagnostic.
  - The reason is the read set (Decision 1(a)). Every session of a checkout
    searches those two locations, with or without the variable, so a record
    created in either is seen by all of them. A record created anywhere else
    would be seen only by sessions that carry the same value: a session of
    the same checkout without it would find no workflow on the branch and
    create a second one.
  - So the variable keeps a checkout's new records in its own homes, today's
    per-worktree layout (for example a checkout whose macro has not been cut
    over, Decision 4), except a dispatched child once the switch is on,
    which goes beside its macro (Decision 3). It does not hide the shared
    records, which that checkout still reads.
  - The checkout must not be a lane, or lie under a lanes directory
    (Decision 5): a lane is removed when its subtask lands, and records
    created in it would go with it. The driver also never removes the
    worktree that holds the effective state root or its own run ledger.
  - It never falls back silently: a fallback would open a second writable
    copy.
- **Who sets it:**
  - the operator, for one checkout;
  - the autopilot driver. It resolves the effective state root once at start
    (an operator value binds, under the rule above for the driven checkout),
    records it in `run.json`, scrubs an inherited value and exports its own to
    every worker. A serial run's workers run in the driven checkout, where the
    value stays valid.
  - **Lanes require shared creation, the default state root, and the macro
    there.** `--lanes 2` or more is refused while the shared-creation switch
    is off, when the effective root is not the default one, and when the
    macro, or an active engineer workflow claiming it, was found anywhere but
    under the default state root (before the cutover it lives in a checkout's
    own home). A lane's read set is the default root and the
    lane: neither a worker nor a session the owner opens inside a lane would
    see records under the driven checkout's own homes.
    - The refusal names each such record and the checkout whose home holds
      it, and the two ways on: the cutover's move (Decision 4, item 4, steps
      1 to 4 and 6), which may be run again after the switch is on and whose
      set (step 4) includes every record such a refusal names, or a serial
      run from that checkout.
- **Creation is checked across the repository.** Once shared creation is
  on, the repository's creation lock is one per persona (and one for
  orchestrator): the one in the default state root's home, wherever the
  record goes. `create` takes it, and so does archive, which today takes its
  own home's creation lock to serialize with create
  (`persona-pipeline/files/scripts/state.mjs:3498-3510`). While the switch
  is off, `create` and archive take only the creation lock of the home they
  write, as today: the default state root is not attested yet, and may not
  be writable (Decision 1(a)).
  - **Older scripts still exclude.** An older script takes only the
    creation lock of the home it writes (`:659-664`). So when, with the
    switch on, `create` or archive writes a home other than the default
    state root's (under the variable), it also takes that home's creation
    lock: the repository's first, then the home's, always in that order;
    with the switch off it takes that home's lock alone. Two hosts creating
    in one linked worktree, one on SR and one older, therefore still meet on
    the lock they share.
  - Under them, `create` (persona and orchestrator) refuses when
    an active workflow for the branch exists in the read set or in the own
    homes of any other worktree of the repository (`git worktree list
    --porcelain`). Today the guard searches the one root it is given
    (`persona-pipeline/files/scripts/state.mjs:2112-2122`) under a lock in
    that root's home (`:659-664`), so two sessions creating in different
    homes would both pass. The scan of other worktrees catches a workflow an
    older persona, or an operator's variable, left in a checkout's own home,
    which no reader outside that checkout sees. It runs whether the switch
    is on or off: a linked worktree's readers already read the main
    worktree's records, so a second active workflow for one branch anywhere
    in the repository would break their lookups by branch. The refusal names
    the worktree and the file that hold the other workflow (Decision 1(a)).
    While the switch is off, two sessions creating in different homes take
    different locks, so the scan narrows the race between them without
    closing it; one that slips through leaves two workflows for a branch
    key, which a newer reader reports as ambiguity, as below.
  - An older script makes no such scan. Until both hosts carry SR, one can
    still create a second active workflow for a branch key in its own
    checkout's home, as today (a second macro on `main` in a linked
    worktree, for example). That is two workflows, never two copies of one:
    a newer reader that sees both reports the ambiguity and its writers
    refuse, naming both files, and the cutover's branch-key check
    (Decision 4, item 4) finds it before the switch.
- **Scrubs, by name:** `SESSION_VARIABLES` (`scripts/lib/session-env.mjs:13-23`,
  docket C88) and the worker's `SCRUB_EXACT` (`worker.mjs:57-71`) list
  `AGENTIC_STATE_BASE`, `AGENTIC_PARENT_WORKFLOW_PATH` (Decision 3) and
  `AGENTIC_AUTOPILOT_TOKEN` (Decision 4, item 5). A test holds both lists to
  all three names.

### Decision 3. B′: the recorded parent path, end to end

- **Dispatch.** `/orchestrator:next` Phase 4 exports
  `AGENTIC_PARENT_WORKFLOW_PATH="$MACRO_PATH"` (absolute) beside
  `AGENTIC_PARENT_WORKFLOW` (`next.md:363-364`). The Codex mirror does the
  same (`plugins/orchestrator/core/skills/next/SKILL.md:166-167`).
- **Bootstrap.** Both templates (`persona-pipeline/regions/verb-bootstrap.md:17-23`,
  `persona-pipeline/regions/verb-bootstrap-profiled.md:20-26`) pass
  `--parent-workflow-path "$AGENTIC_PARENT_WORKFLOW_PATH"` when it is set.
  - The path is valid only with both id variables, so the path alone is
    refused.
  - The ids without the path stay valid: they come from an older
    orchestrator.
- **Create.** `state.mjs create --parent-workflow-path <abs>` (personas with
  `dispatch_target` only) checks that the path is absolute and normalized,
  that its basename is `<parent_workflow>.md`, and that it names an existing
  file in an orchestrator `workflows/` home whose frontmatter has `workflow_id`
  equal to `--parent-workflow` and `workflow_type: macro`.
  - It stores the flat scalar `parent_workflow_path`, immutable once set at
    create, like `parent_workflow` and `originating_subtask`
    (`state.mjs:1155-1158`; ADR-0019 §3, amended).
  - **Once shared creation is on, the child is created beside its macro:**
    in the persona's home under the root that holds the macro file (the
    recorded path's, or the one the candidate search below finds), not under
    `stateRoot()`. Wherever the macro can be found, so can its children: a
    child created under an operator's `AGENTIC_STATE_BASE` while its macro
    sits in the default root would otherwise be invisible to the main
    checkout's finalize and archive guard. While the switch is off, the
    child is created in its own checkout's home, as today, and the recorded
    path is what reaches its macro (Writeback below).
  - The key is optional and needs no schema version: an older reader keeps it
    through its forward-compat carrier, provided it is placed where the
    ADR-0063 S1 note requires.
- **Writeback.** Phase 7 (`persona-pipeline/files/scripts/phase7-commit.mjs:1162-1176`),
  the Stop (`stop-archive.mjs:218`, `:237`) and the orphan sweep (`:428`)
  pass the child's `parent_workflow_path` to `writebackParent`, which tries,
  in order:
  1. **The recorded path, when it names a file.** The file is checked as at
     create. A file that fails is refused with a diagnostic, and the search
     does not go on: a path that names the wrong file is not repaired by
     guessing.
  2. **The candidate search**, when no path is recorded or the path names
     no file (the macro moved at the cutover, or was archived): the
     orchestrator homes of the read set, the default state root's first.
  3. **On every path**, the macro found must have the expected `workflow_id`
     (a new check) and must not be archived, and no other home may hold a
     file with the same id: a second copy refuses the writeback, the
     recorded path included (Decision 4). An archive match is exact
     (`<id>.md` or `<id>-…`), which fixes the prefix match at
     `parent-writeback.mjs:490`. The orchestrator side keeps refusing a path
     inside `archive/` (`plugins/orchestrator/scripts/state.mjs:2434-2441`,
     ADR-0062 §7).
- **Versions.** The path is a hint checked where it is used, so every pairing
  works:

  | orchestrator | persona | writeback |
  |---|---|---|
  | exports the path | records it | through the path, then the candidates |
  | exports the path | older | the older bootstrap ignores the variable: the candidates (today) |
  | older | records it | no path: the candidates, default state root first |
  | older | older | today |

  B′ alone does not make lanes work. Before SR, the recorded path is the only
  thing that reaches a macro in another checkout; after it, the read set
  reaches one under the default state root. Lanes need the Decision 4
  release tuple and the shared-creation switch.

### Decision 4. Rollout: readers first, one writable copy, an operator cutover

The macro orders it PL (B′, storage unchanged) → RR (readers) → SR
(writers find records in the read set; creation stays per checkout) → the
cutover (the tuple on both hosts, any move, then the shared-creation switch)
→ WL, DL → lanes. LR does not depend on storage.

1. **Readers first (RR: runtime and attention).**
   - The entry-brief readers (`entry-brief-readers.mjs:73-79`) and the
     dashboard and doctor workflow readers
     (`plugins/runtime/scripts/lib/state-readers.mjs:706-708`) read each
     persona and orchestrator home's shared records in the read set
     (Decision 1(a)): under the default state root and, when it differs,
     under the checkout.
   - Only the same physical file found twice (the two roots coincide, or a
     path resolves to the same real file) is deduplicated. Two distinct
     files with one workflow id, or two active workflows on one branch, make
     the reader report ambiguity (indeterminate), as the entry-brief readers
     already do by branch, within a home and across two
     (`entry-brief-readers.mjs:372-376`), and block every writer (item 2).
   - **A collision check comes first.** Before RR is installed on either
     host, or pulled into a directory marketplace (item 3), a read-only check
     that RR's runbook gives lists every branch key with an active workflow
     both in the main worktree's homes and in a linked worktree's own homes
     (a macro by its `git_baseline.branch`). The owner finishes, finalizes or
     archives one of each pair first. A pair left over makes that linked
     worktree's readers report the ambiguity and its writers refuse, naming
     both files: closed, but a stop for every run there.
   - A file that disappears between listing and reading (another lane's
     archive, now routine) makes the reader list the directory again and
     re-read it, a bounded number of times, before it reports indeterminate.
     Today one vanished file is indeterminate at once
     (`entry-brief-readers.mjs:316-332`: it lists, then reads each file). A
     persistent read failure or ambiguity still fails closed.
   - The handoff slot stays per checkout (Decision 1(a)), so the readers of
     the slot keep reading only their checkout's: the entry brief's slot
     row (`entry-brief-readers.mjs:504-511`) and attention's handoff reader
     (`plugins/attention/scripts/lib/sensor.mjs:138-146`). The macro's RR
     topic named attention's reader among those that read both; this
     decision narrows it.
   - Their pointers follow Decision 1(c).
   - Runtime and attention compute the state root themselves, by copy
     (ADR-0010 §5).
   - They already feed the serial driver's observer, so both layouts must
     read correctly before any writer moves.
2. **Writers (SR).** Three rules, for every resolver:
   - **Lookups search the read set.** Finding an existing record (by branch,
     by id, by parent) searches the default state root, then the checkout's
     own homes when they differ. A workflow found only in a checkout's own
     home is updated where it is, never copied. One workflow id in two
     distinct files is an error on every write path, as `find-macro`'s
     ambiguity is: never "pick one".
   - **Creation goes to `stateRoot()`**, under the repository-wide check of
     Decision 2, except a dispatched child once the switch is on, which goes
     beside its macro (Decision 3). Until the shared-creation switch is on, `stateRoot()` is
     the checkout's toplevel: SR changes where records are found, not yet
     where they are created.
   - **Every path derived for an existing record comes from that record's
     own home:** its archive directory, its write lock, its peer-run ledgers,
     its consensus task files (Decision 8). The creation locks are the one
     exception: with the switch on, the repository's, then the record home's
     when that is another (Decision 2). Today both
     `archiveWorkflow`s prefer the caller's `repoRoot` over the one inferred
     from the workflow's path
     (`persona-pipeline/files/scripts/state.mjs:3491-3495`,
     `plugins/orchestrator/scripts/state.mjs:4036-4041`). With the record in
     the state root, a Stop in a linked worktree would archive it into its
     own checkout's archive. SR makes the record's home win, and only
     creation uses `stateRoot()`.

   The resolvers SR moves:
   - in the personas: `statePaths` and home selection (the branch-ambiguity
     check counts every home of the read set), stop-archive, and peer-runner
     storage (`persona-pipeline/files/scripts/peer-runner.mjs:93-104`);
   - in orchestrator: `statePaths`, the archive guard and the hooks;
   - next.md's and done.md's `--workflow` resolvers and engineer scans,
     finalize.md's and abort.md's child scans (Decision 1(b)), and their
     Codex mirrors;
   - the observer's homes and its explicit macro lookup.

   **The handoff slot does not move** (Decision 1(a)). The terminal sidecars
   write it beside the workflow today, in the home inferred from the
   workflow's path (persona `state.mjs:2863-2866`, orchestrator
   `state.mjs:562-566`). Both `defaultProjectionFile`s derive it from the
   workflow directory (`persona-pipeline/files/scripts/session-handoff.mjs:232-234`,
   `plugins/orchestrator/scripts/session-handoff.mjs:270-272`), and both
   `projectionFileForWorkflow`s, the Stop backstop's target, from those
   (persona `:250-257`, orchestrator `:289-294`). SR changes all of them to
   write the slot, and its `.footer-rendered` markers, in the checkout the
   command runs in.
3. **Release tuple.** Both hosts install:
   - engineer, founder, designer and orchestrator at or above the SR release;
   - runtime and attention at or above the RR release.

   On Codex an edit reaches an installed plugin only through a release and its
   pin (ADR-0061), and the two hosts are upgraded independently. An older
   persona on either host, working in a linked worktree, looks only in that
   checkout's home. While the switch is off nothing new is created anywhere
   else, and both take that home's creation lock (Decision 2), so SR on one
   host and an older persona on the other never make two copies of one
   workflow. An older script can still create a second workflow for a
   branch key, as today; a newer reader then refuses on the ambiguity
   (Decision 2). Once the switch is on, such a persona would not see a workflow created under the
   default state root and could start a second one for the branch: the
   switch is turned on only after the tuple is verified on both hosts
   (item 4). In the main checkout the old and new rules agree (state root =
   toplevel), so the risk is confined to linked worktrees.

   **On a directory marketplace the pull is the install.** Where Claude
   Code's marketplace is a directory at a checkout of this repository (on
   the owner's machine, the main checkout, `known_marketplaces.json`), Claude
   loads commands, skills and hooks from that checkout's working tree, and
   the plugin root it writes into them is that tree too (ADR-0063 S0 note).
   Only an autopilot worker's scripts come from its pinned roots. So RR's and
   SR's text, hooks and interactive scripts go live there when the owner
   updates that checkout, before any release is installed:
   - that is safe once the collision check (item 1) is clean: they read the
     read set and create where today until the switch is on. On such a
     machine "install the tuple" on Claude means bringing the marketplace
     checkout to a commit that contains it, and the switch (item 4) waits
     until Codex carries the tuple too;
   - SR's runbooks resolve storage through `state.mjs state-root`
     (Decision 6). A pinned or cached script without it fails the block
     before any write, as S3+S4's subcommands do;
   - mid-run, a pull, a branch switch, a commit or an edit in that checkout
     changes what later workers load while the plugin versions stay equal.
     The driver's drift check therefore covers content, not only versions
     (Decision 8, item 4).

   **Every new value or record shape ships its readers first.** A release
   that writes one is used only once the readers are installed on both
   hosts:
   - **The record location.** A record under the default state root, created
     from a linked worktree, is in a place an older reader there never looks.
     SR ships the readers of the read set with creation unchanged. The
     shared-creation switch, turned on by the cutover once the tuple above
     is verified on both hosts, is what starts creating there.
   - The `peer-conflict` gate (Decision 8): today's persona validation
     rejects an unknown gate (`persona-pipeline/files/scripts/state.mjs:1833`).
     CP ships the gate to all three personas and to the driver's gate copy
     in one tuple, with the gate's run id (`awaiting_owner_run_id`), which
     the orchestrator's `plan-conflict` records too. A host still on an
     older persona refuses a `peer-conflict` workflow; it never misreads
     it. The run id needs the whole tuple: on a `decide-conflict` or
     `plan-conflict` workflow an older script keeps it through its
     forward-compat carrier, re-sets the gate without touching it and
     clears only the three gate keys (`:2899`, `:3047`), so no host writes
     a run id until both carry CP.
   - The admission entries of item 5 (`kind: "session"`) are live until
     released, which today's reader does not know. It lists only entries
     named `h-<pid>-<hex>.json` (`ledger.mjs:160`, `:311`), and an
     admission entry is named `s-<admission id>.json`, so it never sees one
     (under an `h-` name it would judge the missing `pid` gone, `:260-270`,
     and delete it, `:366-367`). Either way an older driver ignores the
     admission. SR ships the reader and the writer together, and the tuple
     requires orchestrator at or above SR on both hosts before an
     interactive command writes one.
   - The lock entries of a lanes run keep today's shape (Decision 6): one
     entry per worker group, each judged by today's reader as it judges one
     now. They need no reader first.
4. **The operator cutover** turns shared creation on, once per repository,
   and first moves into the default state root each macro living in a
   linked worktree's own state, as this macro does (the autopilot home
   worktree's), and every child that a linked worktree's own home holds of
   a macro moved or already there. Before the switch, a child dispatched
   from a linked worktree is created in that checkout's home, even for a
   macro of the main checkout (Decision 3), and a child left there would
   keep its macro from lanes (Decision 2). The switch is per repository, so
   all of them move before it. SR writes the runbook under
   `docs/runbooks/`. The steps below speak of one macro; each step covers
   every macro and child being moved.
   1. **Make the repository quiet.** Not only the sessions working on the
      macro write it: every orchestrator Stop hook in that checkout
      snapshots every macro before its archive checks
      (`plugins/orchestrator/scripts/stop-archive.mjs:265-274`, `:146-150`).
      A snapshot reads and writes under the file's lock
      (`plugins/orchestrator/scripts/state.mjs:2679-2700`), so one that meets
      a moved file fails rather than writes it back. The hazards are the move
      itself, which spans many files and is not atomic, and any writer still
      on the old tuple, which looks only where the files were. So:
      - no autopilot run holds the macro (`/orchestrator:autopilot status`,
        then `stop`), and no peer ensemble is pending on it or its children;
      - every Claude Code and Codex session in any checkout of the
        repository is closed. Their Stop hooks are the writers.
   2. **Install** the release tuple on both hosts, and move the autopilot
      home's version pins to it. On a machine whose Claude marketplace is a
      directory at a checkout (item 3), installing on Claude is bringing
      that checkout to the release's commit. Verify the installed versions on
      both hosts before going on: nothing below runs on an older tuple.
   3. **Check that the destination can take it** before moving anything:
      - **A shared root.** `state.mjs state-root`, run in the main checkout,
        reports whether that checkout passes the checks `shared-creation
        --enable` makes (Decision 1(a)), and whether the default state root
        can be written. When either fails, the repository has no shared
        root, and the cutover stops here.
      - **Home kinds.** A state root whose canonical home holds state while
        the move would fill its legacy home (or the reverse) blocks every
        later write: both homes populated is refused today
        (`persona-pipeline/files/scripts/state.mjs:388-395`,
        `plugins/orchestrator/scripts/state.mjs:517-525`). `runtime:migrate`
        moves a home only from legacy to canonical
        (`plugins/runtime/scripts/migrate-workflow-storage.mjs:277-280`), so
        every home involved is brought to canonical first: run it in the
        linked worktree when the source is legacy, and in the main checkout
        when the destination is.
      - **Branch keys.** No active workflow to be moved may share a branch
        key (a macro's is its `git_baseline.branch`) with another active
        workflow anywhere in the repository: in the destination's homes, in
        the own homes of every other worktree (Decision 2's scan), or in the
        set being moved. After the move every linked worktree reads the
        destination, so a pair across two linked worktrees, which no reader
        sees today, would break every lookup by that branch in one of them
        (`plugins/orchestrator/scripts/state.mjs:1074-1080`). The owner
        finishes or finalizes one of each pair first.
      - **Names.** No destination name exists.
   4. **Plan, then move; never copy.**
      - **The set:** each macro file in a linked worktree's own home; every
        engineer workflow, active and archived, found in the own homes of
        every worktree but the main one (Decision 1(b)'s scan), whose
        `parent_workflow` is one of those macros or a macro already under
        the default state root; the
        peer-run ledgers named by each moved workflow's `ensemble_results`
        and `pending_ensemble`, and the macro's own, in the orchestrator
        home's `peer-runs/`; and each moved workflow's consensus task files
        (Decision 8). The handoff slots stay: they belong to the checkout
        (Decision 1(a)).
      - **Plan first.** Before the first move, write the manifest, every
        (source, destination) pair, to
        `.agentic-plugins/runs/cutover/<stamp>.json` under the main worktree.
        Then move each entry and append its `moved` record to the manifest.
        The manifest is kept: until lanes first run, a rollback takes each
        moved record's destination from it (below).
      - **Locks.** Each workflow file moves under its own write lock, the
        lock its writers take. Archived files and peer-run directories have
        no lock of their own: with the repository quiet and no ensemble
        pending (step 1), nothing writes them, and they move under the
        creation locks archive will take once the switch is on: the
        repository's, then the source home's (Decision 2). Step 3 has
        already found the main checkout passing the attestation's checks
        and the default state root writable.
      - **Continue, never guess.** A rerun reads the manifest and judges each
        pair: source present and destination absent, move it; source absent
        and destination present, it has moved; both present or both absent,
        refuse and report the pair (a copy, or a loss). A partial move is
        finished, or reversed by the same rule with the pairs swapped.
      - At the end, check that no source path exists.
   5. **Turn shared creation on** with `state.mjs shared-creation --enable`,
      run in the main checkout, which it checks (Decision 1(a)). Before it
      writes the switch, it appends to the cutover's manifest the inventory:
      the workflow id of every record then under the default state root's
      homes, active and archived, moved or not (a cutover that skipped
      steps 3 and 4 gets a manifest here, holding the inventory only). From
      now on
      `stateRoot()` follows its switch-on rule:
      the default state root unless `AGENTIC_STATE_BASE` names the checkout,
      and a dispatched child beside its macro.
   6. **Verify** with the new tuple, from the main checkout and from the home
      worktree: `find-macro` and `next-ready` resolve the moved macro, the
      driver's preview shows the same subtask states as before, and
      `state.mjs state-root` reports the switch on. Check again that no
      source path has come back, and that no linked worktree's own home
      holds an active child of a macro under the default state root.
   7. **Relaunch.**

   A repository where no linked worktree's own home holds a macro, or a
   child of a macro under the default state root, skips steps 3 and 4. A
   moved child whose macro moved too has a recorded path that now names no
   file, so its writeback takes the candidate search, which finds the macro
   under the state root (Decision 3); one whose macro stayed keeps a path
   that still names it.

   **Rollback** exists only until lanes first run. Once a lane has existed,
   its workflows are in the state root, and the old tuple reads the checkout
   it runs in: no single home serves both the old orchestrator's scans and
   the lanes' workflows. After that point a problem is repaired forward: the
   driver records its first lane's creation in the switch file
   (`lanes_first_run_at`), and rollback refuses once that is set. Before
   it, rollback reverses the cutover with the same quiet repository,
   preflight, plan-first manifest rules and locks:
   - plan first: find the records, their destinations and every refusal
     below before anything changes, so that a refused rollback leaves the
     switch on;
   - then turn shared creation off (`state.mjs shared-creation
     --disable`), so that nothing more is created under the default state
     root, and move. What the rollback needs from the cutover is in its
     manifests, not in the switch file;
   - **the records are found afresh, and judged by identity.** Work since
     the cutover may have archived a moved workflow, which leaves both paths
     of its manifest pair absent, so the rollback finds each record where it
     is now, by its workflow id, under the default state root's homes,
     active or archived. Each goes back to a checkout's home, into the same
     kind of directory (`workflows/` or `archive/`) it is in now:
     - a record the cutover moved goes to the checkout the cutover's
       manifests name as its source. The manifests map each workflow id to
       its source checkout, and are kept until lanes first run for this;
     - a record whose id is in the inventory (step 5) and was not moved
       stays: it was in the main checkout's home before the cutover;
     - a record whose id is in neither was created after the switch was
       turned on. When its `repo_root` is not the main worktree it goes to
       that checkout: written at create
       (`persona-pipeline/files/scripts/state.mjs:2137`,
       `plugins/orchestrator/scripts/state.mjs:2572`), it names the
       creating checkout (Decision 1(b)), and nothing has moved such a
       record since. Otherwise it stays.

     `repo_root` is never read for a record the inventory holds: one moved
     by hand records where it was created, not where it lived (this macro,
     Decision 1(b)). Identity, not a timestamp, separates old records from
     new: the creation times are in whole seconds, so a record created in
     the switch's second could fall on either side.

     Each record takes its peer-run ledgers and consensus task files with
     it. The rollback writes its own manifest before it moves anything. The
     cutover's manifests also continue or reverse a cutover interrupted
     before step 5, by step 4's rule;
   - a record whose checkout is gone, or is a lane, is refused and
     reported: no home the old tuple reads would hold it;
   - refuse while an active macro and a child it still needs would end in
     different checkouts' homes, in either direction (a macro of the main
     checkout with a child dispatched from a linked worktree, or the
     reverse). A child it still needs is an active one, or an archived one
     that a subtask not yet completed, deferred or abandoned names as its
     `engineer_workflow_id` (a commit waiting to land). The old tuple's
     writeback and its child scans each search one checkout
     (`persona-pipeline/files/scripts/parent-writeback.mjs:73-80`,
     `plugins/orchestrator/scripts/state.mjs:4381-4388`), and its driver
     looks for such an archived child in its own checkout's archive only
     (`plugins/orchestrator/adapters/claude/autopilot/observe.mjs:203-208`),
     halting `owner-choice` when it is missing (`policy.mjs:280-281`). The
     owner lands and records that subtask, or finishes or detaches that
     child, first. Any other pair with an archived member moves as found:
     the child scans read `workflows/` only (`:4385-4388`), and an archived
     child writes back no more;
   - refuse if a destination exists, and check that no source path is left;
   - then reinstall the old tuple.

   Only renames under the writers' own locks are used, with every writer
   stopped, so neither direction makes a second copy. The old tuple must not
   run while any record the rollback sends to another checkout's home is
   still under the default state root.
5. **What the owner's main-checkout session sees.** After the cutover, a
   macro whose integration branch is `main` is active on `main`: ADR-0018
   §sub-2 keys a macro by `git_baseline.branch`.
   - So the owner's session on `main` shows it in the entry brief, the
     dashboard and `/orchestrator:resume`. That is intended: as in the
     precedent, the main session is the control center. A run it works
     beside is launched from another checkout, since done and finalize read
     the driver's own checkout (Decision 6, Policy).
   - It must not race the driver. A read-only check of the lock would leave
     a gap before the driver takes it, so the interactive commands that write
     the macro or switch a branch take part in the locks a run takes
     (`ledger.mjs:376-423`), as **admission entries**:

     | | |
     |---|---|
     | **Who** | `/orchestrator:next`, `/orchestrator:done`, `/orchestrator:finalize`, `/orchestrator:abort` and `/orchestrator:resume`'s archive action, on Claude and in their Codex mirrors (`plugins/orchestrator/core/skills/<name>/SKILL.md`). |
     | **Which locks** | Each joins the macro lock. `/orchestrator:next`, the one command that switches a branch (`next.md:301-315`), first joins the worktree lock of the checkout it runs in (`worktreeLockPath`, `ledger.mjs:142-144`): the order the driver takes them (`driver.mjs:351-352`). Without it, `/orchestrator:next --workflow=B` could switch the branch under a run of macro A, whose macro lock B's command never meets. |
     | **Holder** | An entry `{kind: "session", admission_id, command, macro_id, checkout, host, session_id, acquired_at}`, in a file `s-<admission id>.json` in each lock the command joins. `state.mjs admission join --macro <id> --checkout <path> --command <name> --host <host>` draws the admission id (128 random bits, hex), writes the entry in every lock that command joins under that one id, and prints it. `session_id` is the host session's id when the runbook can read one, for display only. The entry names no pid: a runbook block's process ends with the block, and the host session's process outlives a release the runbook never reached. |
     | **Liveness** | Live until it is released.      | **Join point** | After the command's read-only precondition checks, right before its first guarded action: `/orchestrator:next` after Phase 2's clean-tree, engineer-root and ownership checks (`next.md:229-285`) and Phase 3's engineer preflight, which today runs after the switch (`:323-333`) and moves before it, and before its switch (`:287`); `/orchestrator:done` after `resolve-landing` (`done.md:276-280`), or in `--no-commit` mode after Phase 3a's active-child check, and before its `subtask-update`; the others before their first write. A routine refusal (a dirty tree, `not_merged`) therefore exits before the join and leaves no entry. A precondition a run's step could have changed before the join is read again after it, in the first guarded block, unless the guarded write checks it itself (`subtask-update` checks ownership and provenance atomically, `done.md:307`). |
     | **Admission** | `join` adds its entries and proceeds only when no other live entry exists in any lock it joins (a run's or another session's, whatever its command or macro); otherwise it removes its own and refuses. No entry is ever replaced: two live sessions in one checkout and host cannot be told apart from a dead one, and a replaced session could still be inside a step no check guards (`/orchestrator:next`'s Phase 4 runs the engineer runbook). A driver starting meanwhile sees the entry and halts `owner-choice`. |
     | **Guarded actions** | Each block that switches the branch, writes the macro, or dispatches into the checkout first runs `state.mjs admission check --macro <id> --checkout <path> --admission <admission id>`, which checks every entry the join wrote (for `/orchestrator:next`, the worktree lock's and the macro lock's), and stops before acting when any is gone. The dispatch is `/orchestrator:next`'s Phase 4 prelude (`next.md:357-386`), and any re-emission of it at the top of an engineer block: the engineer bootstrap that follows creates the child on whatever branch is then checked out (`persona-pipeline/regions/verb-bootstrap.md:9`, `:26-38`), so a session whose admission is gone must not reach it. The runbook carries the id from block to block as it carries the macro path. A check and the action after it are two processes (a `git switch` is git's own), so a release between them goes unseen: the guard narrows the race to that gap, it does not close it. It does stop a session resumed after its entry was released: each checks its own id, never another session's entry. |
     | **Release** | `/orchestrator:next` after Phase 5 records the subtask in progress (from then on the driver's own claim rules see it); the others after their last write. A session that dies between blocks leaves its entries; the owner removes them with the same command, the id shown in the refusal and in `status`, once they know that session is gone. |
     | **Refusal** | It names the holder. A run: its id, the checkout it was launched in (both from the lock entry), and `/orchestrator:autopilot status` to run there, which today looks only at the runs of the checkout it is run in (`autopilot/cli.mjs:311-320`). A session: its command, checkout, host, session id when recorded, age and admission id, with the release command. |
     | **Workers** | The holding run's workers pass without an entry. A worker proves it with a per-run secret: the driver draws 128 random bits at start, stores only their SHA-256 in its lock entry (the lock files are readable), and exports the secret to its workers as `AGENTIC_AUTOPILOT_TOKEN`. A caller passes when its `AGENTIC_AUTOPILOT` names the holding run and its token hashes to the stored digest. Every other session is refused, a worker of another run included. A process group is no proof: a worker's descendants can leave it (`worker.mjs:182-185`). |
     | **Where** | The lock primitive moves from the Claude adapter (`autopilot/ledger.mjs`) to `plugins/orchestrator/scripts/`, since the Codex mirrors use it too. The driver imports it from there. |

   - `/orchestrator:plan` and `/orchestrator:approve` stay available. A
     re-plan revokes the approval, and the driver halts at its next decision
     (ADR-0063 S6 note). An approval is the owner's own act.
   - SR implements this, because SR makes the macro visible.

### Decision 5. Lanes: placement, ownership, lifecycle, reconciliation

- **A lane** is one subtask attempt's git worktree, on `subtasks[i].branch`,
  at `<P>/<M>-lanes/<macro-id>/<subtask-id>`.
  - `M` is the main worktree's directory name and `P` its parent: the
    repository's identity, not the launching checkout's. Here that gives
    `…/agentic-plugins-lanes/…`, never `…/agentic-plugins-autopilot-lanes/…`.
  - A repository with no shared root refuses `--lanes`: one whose git common
    dir is not named `.git` (as a bare repository's usually is), where each
    worktree's default state root would be its own, and one whose main
    checkout cannot be attested (a separate git dir, a bare repository),
    where the switch that lanes require is never turned on (Decision 1(a)).
- **Ownership is a git worktree lock.** The driver creates a lane with
  `git worktree add --lock --reason "agentic-autopilot <macro-id> <subtask-id>"`.
  - Creating the worktree and marking it as the driver's are one git
    operation.
  - A locked worktree refuses `git worktree remove`, and `prune` keeps it.
    Measured 2026-10-07 on git 2.54 in a scratch repository.
  - The run ledger records each lane event, but the lock reason, not the
    ledger, proves ownership.
  - The lock marks ownership; it excludes no one from running commands. A
    run that drives a lane also holds that lane's worktree lock
    (`worktreeLockPath`, `ledger.mjs:142-144`) while it does, so no second
    run drives it. A session the owner opens inside a lane is not excluded,
    as in the driven checkout today.
- **Creation** happens in the decision that spawns the lane's first step,
  and only once that step is admitted: the run is not draining, the
  throttle lets a new lane start, and the step's reservation is made
  (Decision 6). The spawn follows the creation. No lane is created ahead of
  its step, so a throttle wait, a reservation wait or a drain leaves no
  lane behind without its step. A crash between the creation and the spawn
  can, and so can a first dispatch that ends (interrupted, stopped or
  failed) before it creates the subtask's child: reconciliation row 4.
  1. `git fetch --no-tags --refmap= origin +refs/heads/<baseline>:refs/remotes/origin/<baseline>`.
     It writes that one remote-tracking ref (and `FETCH_HEAD`), whatever the
     remote's configuration. Measured 2026-10-07 on git 2.54 in scratch
     repositories: an explicit destination like this one follows tags
     without `--no-tags` (and `remote.<name>.tagOpt` can add tags to any
     form); and with an extra `remote.origin.fetch` mapping configured, it
     also updated the mapped local ref until the empty `--refmap=` told git
     to ignore the configured mappings (git-fetch(1), `--refmap`). When the fetch fails,
     the last fetched ref is used, with a warning in the ledger (next.md's
     rule, `next.md:304-306`); with no such ref the run halts `owner-choice`.
     Then the subtask rows of reconciliation (below) run again for this
     subtask: a branch can appear, or be checked out, while a run goes on.
  2. When the branch is absent:
     `git worktree add --lock --reason … --no-track -b <branch> <lane> refs/remotes/origin/<baseline>`,
     as `/orchestrator:next` creates it (`next.md:311`). This writes one ref,
     `refs/heads/<branch>`, and sets no upstream (measured 2026-10-08, git
     2.54, as are `unlock` and a re-`lock` with the same reason, which step 3
     of Removal uses). When the branch exists and reconciliation accepts
     it: `git worktree add --lock --reason … <lane> <branch>`. A `worktree
     add` that fails (the branch checked out elsewhere meanwhile, the path
     taken) halts `owner-choice` with git's reason; it is never retried with
     `--force`.
  3. Write the lane's identity, a random lane id, to
     `<lane>/.agentic-plugins/runs/autopilot/lane.json` (per checkout,
     ignored), then record the creation with that id in the run ledger.
     A worktree created later at the same path, by the driver or by the
     owner, has no such file or another id.
  - `/orchestrator:next` then runs in the lane, finds the branch existing and
    takes its switch path (`next.md:301`), which skips its own fetch. The
    driver's fetch is therefore what keeps ADR-0062 §Decision 2's base rule.
- **Steps.** A worker in a lane runs with `cwd=<lane>` and
  `AGENTIC_STATE_BASE=<the default state root>` (lanes require it,
  Decision 2).
  - Dispatch, verbs and commit run in the lane.
  - `/orchestrator:done` and `/orchestrator:finalize`, which never switch
    branches, run in the driver's own checkout.
  - The checks that read a checkout run on the checkout the step runs in
    (Decision 6, Policy).
- **Removal.** Once `/orchestrator:done` records the subtask completed, the
  driver removes the lane, never with `--force`, and only when the lock
  reason is its own:
  1. **Check, while the lane is still locked,** that it is clean and holds no
     shared state: each shared-record directory of Decision 1(a) in the lane
     (the persona and orchestrator homes' `workflows/`, `archive/`,
     `peer-runs/` and `consensus/`, and the legacy homes') is absent or
     empty. `git worktree remove` deletes ignored files without `--force`
     (measured 2026-10-07, git 2.54), and those directories are ignored. A
     record there was written by an older persona, or by an owner or Codex
     session in the lane, and would be lost.
  2. **Record a removal intent** in
     `<main>/.agentic-plugins/runs/autopilot/lanes/<macro-id>.jsonl`, beside
     the macro lock, since the unlock erases the ownership proof. It names
     the lane's path and its lane id (Creation, step 3). It is macro-scoped,
     not in the run directory, so a run launched from another checkout finds
     it.
  3. **`git worktree unlock`, then `git worktree remove`.** If the remove
     refuses (the lane changed after the check), lock it again with the same
     reason, record it `kept` in the intents file, which closes the intent,
     and report it.
  4. **Record the removal `done`** in the intents file, which closes the
     intent.
  - An intent is open until a `done` or `kept` record follows it. An open
    intent proves ownership of an unlocked worktree only when that worktree's
    `lane.json` carries the intent's lane id (row 9 below): a removal that
    succeeded just before a crash leaves an open intent, and the path may
    since hold another worktree.
  - A lane that fails step 1 is kept and reported.
  - Lanes are kept on halt and on interrupt.
  - The branch stays; the owner prunes it.
  - The ignored files a removal does delete are the lane's own per-checkout
    artifacts (Decision 1(a)), which describe only that lane.
- **Reconciliation** runs at the start of every run with lanes, before the
  first decision, and its subtask rows (10–12) run again before each lane is
  created (Creation above). A serial run does not reconcile lanes
  (Decision 6). It compares `git worktree list --porcelain` with the macro and the
  run ledgers.

  Before the rows, the run:
  - fetches `origin/<baseline>` as Creation step 1 does, with its fallback
    and its halt. Every tip check below compares with
    `refs/remotes/origin/<baseline>` as that left it;
  - finishes every dead run's cleanup from the open-run records, and reads
    the removal intents of the macro (Decision 6, Locks; Removal above),
    and records `done` for every
    open intent whose path `git worktree list` no longer shows: that removal
    finished before a crash;
  - gives a lane id to every worktree that carries our lock reason, exists,
    and has no `lane.json` (a crash between `worktree add` and the identity
    write, Creation step 3). It writes the file while the lane is still
    locked, and records it in the ledger: the lock reason proves the lane is
    ours, and without an id every later recovery of it would refuse it
    (row 9).

  The rows come in four groups. Within a group they are checked in order, and
  the first that matches decides.

  **Our lanes:** each worktree that carries our lock reason. Row 1 comes
  first, so no later row acts on a lane that is gone.

  | # | found | action |
  |---|---|---|
  | 1 | the lane's directory is gone | halt `owner-choice`, naming the lane and the owner's commands, `git worktree unlock <path>` then `git worktree prune`. The driver never prunes: prune has no path selector, and between a dry run and the prune another worktree can become prunable, whose metadata is not ours. Until then git keeps the branch registered there, so the subtask cannot have a new lane |
  | 2 | its subtask is no longer in the plan | keep it, report it: the owner removes it |
  | 3 | the lane's branch is no longer the plan's | halt `owner-choice`: the plan moved the subtask, and a lane is never re-pointed |
  | 4 | the subtask is pending and no engineer workflow claims it | a prepared lane, whose subtask no step has claimed yet: a crash between the lane's creation and the spawn of its first step, or a first dispatch that ended before it created the child (Creation). Dispatch into it once next-ready reports the subtask ready, and only while the lane's branch tip equals the baseline ref. A tip that differs means the baseline moved since the lane was cut (a predecessor landed, ADR-0062 §Decision 2): halt `owner-choice`, naming the lane and its branch for the owner to remove |
  | 5 | the subtask is pending and an engineer workflow of the macro claims it | halt `owner-choice`, as today (`policy.mjs:380-395`): the dispatch stopped before it recorded the subtask in progress (`next.md:390-410`, Phase 5); re-attach with `/orchestrator:next <id>` |
  | 6 | the subtask is in progress on that branch, clean or dirty | adopt it (this covers a creation that succeeded before its ledger write) |
  | 7 | the subtask is completed, and the lane passes the removal check | remove it (cleanup interrupted after done) |
  | 8 | any other case (completed but failing the removal check, deferred, abandoned) | keep it, report it |

  **Unlocked worktrees at our lane paths:**

  | # | found | action |
  |---|---|---|
  | 9 | an open removal intent names this path, and the worktree's `lane.json` carries its lane id | it passes the removal check: finish the removal (a crash between unlock and remove) and record it `done`. Otherwise lock it again with our reason, record it `kept` in the intents file, report it. An unlocked worktree whose `lane.json` is missing or carries another id is not ours: row 13 |

  **Subtasks the run would give a lane:** a pending subtask that next-ready
  reports ready, or an in-progress one whose engineer child is live, when no
  lane of ours holds it. A completed subtask, one waiting to land, a blocked
  one and one with a lane are not checked here.

  | # | found | action |
  |---|---|---|
  | 10 | in progress, its live child on branch B, and B checked out in no worktree (a serial run's subtask, or a lane lost mid-subtask after row 1's commands) | give it a lane at its next step: Creation adds a locked lane on B (the existing-branch form above) once that step is admitted, and the step adopts it |
  | 11 | its branch is checked out in a worktree that is not one of our lanes, the driver's own checkout included | halt `owner-choice`, naming the worktree; for the driver's own checkout, say to switch it off that branch and relaunch. Never `--force` |
  | 12 | pending, its branch exists, and no workflow of the macro claims it | reuse the branch only when its tip equals the baseline ref. A branch behind would omit a landed predecessor, and one ahead would carry foreign history (ADR-0062 §Decision 2): halt `owner-choice` |

  **Everything else:**

  | # | found | action |
  |---|---|---|
  | 13 | a worktree under the lanes directory without our reason, or with another macro's | report it; never touch it |

- **Preflight per lane.** The four `.agentic-plugins/` directories must be
  ignored in each lane, as in the driven checkout (`driver.mjs:55`, `:97-99`).

### Decision 6. The scheduler

- **`--lanes N`.** Absent or 1: today's serial driver (one subtask at a
  time, in the driven checkout). It keeps its policy and gains what is not
  lane-specific: Decision 7's event, the admission entries and worker token
  (Decision 4, item 5), the content drift check (Decision 8, item 4), and
  the dead-run cleanup below. 2 or more: lanes.
  - The owner's default cap is 2. The proposals (Decision 8) never suggest
    more. A larger N is the owner's explicit choice: it prints the
    rate-limit cost, and the throttle still gates each new lane.
  - **A run resumes with its own macro and `--lanes`.** The halt record's
    and `printHalt`'s relaunch command repeat the run's `--macro <id>` and
    `--lanes N`. Today it is a fixed `start --execute`
    (`driver.mjs:212-215`), which finds the macro from the current branch
    (`autopilot/cli.mjs:53`, the lookup at `observe.mjs:164-171`), and with
    lanes the run is proposed from a checkout no one works in, often one
    off that branch (Policy below; Decision 8, item 4). A serial run refuses at start while a lane with our lock reason
    holds a subtask that is not completed, and names the lanes command, with
    `--macro <id>` and `--lanes N`: it does not reconcile lanes,
    and would halt on their active children (`policy.mjs:470-473`) or ask
    for a switch to a branch git will not check out twice (`:502-506`).
  - Lanes require shared creation, the default state root and the macro
    there (Decision 2), and a capability floor, never read from version
    numbers. S8's floor is a search of the
    pinned sources for tokens (`roots.mjs:96-116`, `autopilot-preflight`
    among them at `:107`) plus a run of the pinned engineer's `state.mjs
    --help` (`:130-133`, `plugins/orchestrator/scripts/discover-engineer.mjs:379-388`).
    Lanes add, the same two ways:
    - the pinned engineer and orchestrator `state.mjs` answer
      `state-root --repo-root <checkout>`, a read-only subcommand that
      prints the resolved state root, whether shared creation is on, and,
      in the main checkout, whether it passes the checks of the attestation
      (Decision 1(a)) (run). SR adds it; the runbooks use it too, to resolve storage in
      shell;
    - the pinned engineer's `create` accepts `--parent-workflow-path`
      (token, PL);
    - the pinned runtime's entry brief reports the state root it read (run,
      RR).
  - A subtask already in progress on a branch checked out in the driver's
    own checkout (left by a serial run) cannot get a lane, since git checks
    a branch out in one worktree only: reconciliation row 11 halts.
- **Policy.**
  - More than one active child is allowed when each one's branch is checked
    out in its own lane. With lanes this replaces `policy.mjs:470-473`;
    serial runs keep it.
  - A child active on a branch no lane holds, and checked out somewhere,
    halts `owner-choice` (row 11); checked out nowhere, it gets a lane
    (row 10).
  - **A subtask with a step in flight is left alone** until that step ends.
    It is excluded from readiness (`next-ready` may report it ready again)
    and from every per-subtask check. While its step runs, states that are
    halts between steps are normal: a pending subtask claimed by its new
    child (Phase 5 records it in progress only after the whole first verb,
    `next.md:390-410`; `claimProblem`, `policy.mjs:380-395`), a pending peer
    ensemble (`:306-308`), a commit phase (`:313-316`, which would otherwise
    send a second commit worker into the lane). When the step ends, its lane
    is judged from a fresh observation, by the rules above. The macro-wide
    claim check excludes those subtasks too.
  - Approval, macro gates and version drift stay global. They are checked
    before any lane's step.
  - **The checks that read a checkout run on the checkout a step runs in:**
    the entry-brief guard (`policy.mjs:238-261`), the foreign-workflow check
    (`observe.mjs:307-329`, `policy.mjs:462-464`) and the detached-HEAD halt
    (`policy.mjs:450`). With lanes, each lane is checked before its own
    step, and the driver's own checkout before each done or finalize, which
    run there. So work in the driver's checkout still halts a lanes run at
    its next done: once the macro is active on that checkout's branch
    (`main`, after the cutover; Decision 4, item 5), an owner's workflow
    there makes the brief show two live workflows (`policy.mjs:244-249`) or
    lead with a command outside the allowlist, a foreign workflow trips the
    foreign check, and a checked-out commit the detached-HEAD halt; the halt
    drains every lane. A lanes run is therefore proposed from a checkout no
    one works in (Decision 8, item 4). A serial run keeps the checks on the
    driven checkout.
- **Per-lane fingerprint.** It hashes the lane's git (branch, HEAD,
  porcelain), its engineer child, and only its own subtask's fields
  (`status`, `engineer_workflow_id`, `commit`, `pr_url`, `closed_at`).
  Another lane's progress never satisfies this lane's no-progress check. Steps
  outside a lane (done, finalize) keep the macro-wide fingerprint.
- **Ledger.** One run directory in the driver's checkout, as today.
  - Each `steps.jsonl` record carries `lane`: the subtask id, or null for a
    step outside a lane.
  - `seq` stays run-wide, so the ledger keeps one total order.
  - `lanes.jsonl` records lane events: created, adopted, removed, kept,
    reconciled.
  - `run.json` gains the effective state root and a lanes summary.
- **Locks.** The macro lock keeps its place (`ledger.mjs:137-140`), its
  exclusion (`acquireLock`, `:391-423`) and its entry shape. Each run also
  holds the worktree lock of every checkout it drives: its own, and with
  lanes each lane's (Decision 5).
  - **One entry per worker group.** Beside its own entry, a run adds one
    entry for each worker group in flight, recording the driver (pid,
    fingerprint) and that group in the `worker` field: today's `{pid, pgid,
    fingerprint, session_id}` (`driver.mjs:419`), plus the lane and its cwd,
    which are new. It removes the entry once the group is
    empty. Today's reader (`holderAlive`, `ledger.mjs:260-270`) judges each
    entry live while the driver or that one group lives, so a dead driver
    with any lane worker alive still holds the lock, for an older reader
    too. A single entry listing several groups could not do that: an older
    reader sees one `worker`, and once that group ended it would delete the
    entry (`:366-367`) while another group still ran. A serial run keeps
    `setWorker` on its own entry, as today.
  - `stop` and `status` group the entries by run id, and find and empty
    every group.
  - **A dead run is cleaned up, not forgotten.** A dead driver leaves what
    only it would have cleaned up: peers run detached from the worker groups
    (`driver.mjs:194-196`), and today `stop` on a dead driver empties the
    worker group and reports success (`autopilot/cli.mjs:371-378`). So
    `stop`, and the next run, cancel the dead run's pending peer runs, and
    only those: the driver kills only what its steps started
    (`driver.mjs:14-16`).
    - peer-runner records the caller's `AGENTIC_AUTOPILOT`, the run id every
      worker carries, in each run's handle at spawn;
    - the cleanup cancels a pending run, through peer-runner's
      fingerprint-checked `cancel` (as below), only when its handle names the
      dead run. A peer the owner started after the crash, in a kept lane or
      anywhere else, names none and is left alone. A pending run from an
      older peer-runner, which names none either, is reported, not
      cancelled;
    - each unfinished step's reservation is recorded as spent in its
      `run.json`.

    Only then is the run reported stopped.
  - **An open-run record finds a dead run.** The next run may start in
    another checkout, and the lock entries cannot be the pointer to a dead
    run's ledger: an older driver's `acquireLock` (`ledger.mjs:409`) deletes
    entries judged gone (`:260-270`, `:366-367`), as would any new consumer
    that reuses its cleanup, so the pointer can vanish before a newer run
    reads it. Each run therefore writes
    `<main>/.agentic-plugins/runs/autopilot/open/<run-id>.json` before its
    first spawn, beside the macro lock and outside every lock directory: the
    run id, the macro id, the checkout and run directory of its ledger, and
    the driver's pid and fingerprint. No lock consumer lists that directory.
    - The run removes its record when it ends with every worker group
      empty: completed, halted, interrupted.
    - `stop`, and every run at its start, list the records for this macro
      and judge each driver by its pid and fingerprint, as `holderAlive`
      judges a lock entry's. A dead driver's worker groups are empty by then:
      a starting run holds the macro lock, so none of them is live, and
      `stop` empties them first. For a dead one they read its ledger, where
      every `started` line without its `finished` line is an unfinished step
      (`ledger.mjs:9`, `:99`), do the cleanup above, and only then remove
      the record. Each part of the cleanup is idempotent (a step's
      reservation is settled once, by its `seq`; a cancelled peer run stays
      cancelled), so a `stop` and a starting run that meet the same record
      count nothing twice. A record whose ledger is gone (its checkout
      removed) is reported and kept; the owner deletes it once they have
      checked that run's peers.
    - Lock entries are then only exclusion, as today: whoever clears one
      judged gone loses nothing.
- **Peer cancellation.** After a failed or aborted step, the driver cancels
  the runs that became pending during that step on that step's own
  subtask's engineer workflows, with their ledger in each workflow's own
  home (Decision 4, item 2).
  Today it cancels the runs that became pending during the step on any
  workflow of the macro (`driver.mjs:181-192`), which with lanes would reach
  another lane's peers.
- **Budgets are reserved.**
  - Before a spawn, the driver reserves one step and
    `min(per-step cap, run cap − spent − reserved)` dollars. It does not spawn
    when that is below the minimum (`driver.mjs:49`).
  - Every way a step can end settles the reservation: an exit, an abort, a
    spawn error, a lane creation that halts before the spawn (Decision 5),
    a missing cost report. The reported cost is spent, or the
    whole reservation when no cost was reported (nothing for a lane creation
    that halted before the spawn), and the reservation is released.
  - A start blocked only by other steps' reservations waits for them to
    settle, then decides again. The budget is exhausted only when what is
    already *spent*, the steps already *taken* or the elapsed time leaves
    too little: a $25 run whose first step reserved $25 is not exhausted, and
    may continue once that step spends $1.
  - Each worker's time is bounded by the run's deadline, as today.
- **Drain (W2).** A halt in any lane or in a lane's creation (Decision 5),
  an invalidated plan approval, version drift, or an exhausted budget puts
  the run in `draining`:
  - no new lane starts or is created, and no lane starts a new step;
  - steps in flight run to their normal end and are verified and recorded. A
    commit that finishes still emits its landing-ready event (Decision 7),
    and a halt during the drain is recorded too;
  - when nothing is in flight, the driver writes `halt.json`, with the first
    halt as `reason` and one entry per lane, and exits 2.
- **SIGINT and SIGTERM do not drain.** Every group in flight is aborted
  (`interrupted`), during a drain too. Lanes are kept, and locks are released
  once every group is empty (the S8 rules).
- **Throttle**, with lanes only. The driver reads every `rate_limit_event`
  from every worker stream; events repeat during a stream, so a worker in
  flight keeps them fresh. Their fields, as observed (§Context):
  - a top-level `status` (`allowed`, `allowed_warning` or `rejected`), with
    `rateLimitType` naming the window that status describes (`five_hour` or
    `seven_day`) and `resetsAt`, that window's reset;
  - on a warning, a top-level `utilization` of that window, and on some a
    `surpassedThreshold`; on `allowed` and `rejected`, overage fields;
  - `unifiedWindows.five_hour` and `.seven_day`, each a `utilization` and a
    `resetsAt` (one event of 802 had no `five_hour`).

  Every `resetsAt` is in Unix seconds. The status speaks for one window
  only: when it names `seven_day`, the five-hour window's status is not in
  the event, only its utilization.
  - **The state is kept per window, not per event.** For each window the
    driver keeps the last status an event gave for it (an event updates
    only the window its `rateLimitType` names, with the top-level
    `resetsAt` as that status's reset) and the last utilization
    `unifiedWindows` gave for it (with that window's `resetsAt`). A newer
    event about one window never erases what is kept for the other: a
    seven-day warning that arrives after a five-hour refusal leaves the
    refusal in place.
  - **A new lane** is a lane's first step in this run: the step of a lane
    created for it, or the first of a prepared or adopted lane. The throttle
    gates only that step, and a lane is created only once that step is
    admitted (Decision 5, Creation), so a throttled run creates no lane.
  - **Each kept part expires with its own window:** it is dropped once its
    reset has passed. A part with no numeric reset time is kept until a
    later event for the same window replaces it. So a seven-day `rejected`
    outlives a five-hour reset, and a five-hour refusal ends with its own
    window.
  - The state is then decided in this order. All three rules are the
    owner's (§Context): rule 1 and the first sentence of rule 3 are the
    reading of 2026-10-07; rule 2, the behaviour before the first event, and
    rule 3's last two sentences, a case that reading left open, were
    decided on 2026-10-08. Rule 2's other case, no five-hour utilization
    kept although events came (dropped at its reset, or never reported), is
    this ADR's: it applies the owner's rule for the time before the first
    event:
    1. **Throttled:** a kept status `rejected`, for either window; or a kept
       five-hour status other than exactly `allowed`; or a kept five-hour
       utilization that is a number of 0.85 or more. Explicit evidence
       decides even when another part is missing.
    2. **Unknown:** no event in this run (the state is not persisted
       across a relaunch), or no kept five-hour utilization that is a
       number in [0, 1]. A new lane starts only while no worker is in
       flight, and that worker's first event, which comes with its first
       model response, decides the next.
    3. **Open:** otherwise. A known five-hour utilization below 0.85 with
       no five-hour status kept (the events named only `seven_day`) is
       open: each of the 11 five-hour warnings measured came at a
       utilization of 0.92 to 0.99, past `surpassedThreshold` 0.9, and so
       above 0.85. Read as unknown, that case would hold new lanes back,
       while such a worker runs, on the seven-day warning alone: 42 of the
       140 measured streams (§Context).
  - **The seven-day window is reported, never gated**, its
    `allowed_warning` included: the driver shows the seven-day utilization
    and its reset in the run line and the final report. Only a `rejected`
    status stops new lanes there (rule 1).
  - **Throttled with nothing to refresh it**, that is no worker in flight
    and no started lane with a runnable step: wait until each part that
    throttles has expired, then decide again. When one has no reset time, or
    its reset falls after the run's deadline, halt `budget`, naming the
    rate-limit window. A started lane with a runnable step is not
    "nothing": it steps, and its worker brings new events.
  - Lanes already started keep stepping: the throttle gates new lanes only,
    the owner's default.
- **Forced resume.** `--next <step>` keeps its grammar, and with lanes it is
  judged per lane:
  - With more than one active child it needs `--lane <subtask-id>`, and is
    refused without it. A relaunch may give one `--lane <id> --next <step>`
    pair per lane.
  - `forcedApplies` (`policy.mjs:549-573`) is judged on the targeted lane
    alone: a verb or a commit needs that lane's child active, where today it
    needs exactly one active child in the run (`:554`); a dispatch needs no
    active child on that subtask, where today it needs none in the run
    (`:559`).
  - A forced step replaces only its own lane's judgment halts. The forced
    steps start first. The other lanes are then judged as usual, and a
    judgment halt that persists in one of them drains the run while the
    forced steps finish.
- **Lanes waiting to land do not hold capacity.** The cap bounds concurrent
  workers: their cost, the rate limit, a full test run each. A lane waiting
  for its merge runs nothing. The backlog is bounded by the plan and reported
  by Decision 7. The run halts `awaiting-landing` when nothing else can run,
  as today.
- **Final report:** one block per lane, then the run line.

### Decision 7. The landing-ready event (docket C118)

- **When.** In serial runs and in lanes. The observer sees a subtask committed
  and not landed: its engineer workflow is archived terminal and not
  `close-complete`, and `resolve-landing` answers `no_pr` or `not_merged`
  (`observe.mjs:244-245`, `:331-345`; `policy.mjs:336-360`). The driver
  emits one event, and the run keeps dispatching.
- **The commit** is captured from `refs/heads/<branch>` when the event is
  emitted: from git, not from a note (ADR-0063 R5).
- **Content:**
  - the subtask id, engineer workflow id, branch, captured sha and
    integration branch;
  - the push and pull-request commands (`landingList`, `policy.mjs:363-374`);
  - an overlap report and a merge order.
- **Overlap check, read-only.**
  `git merge-tree --write-tree --name-only --no-messages <a> <b>` exits 0
  when the two merge clean, and 1 with the conflicted paths when they do not.
  The check runs:
  - against `refs/remotes/origin/<baseline>`;
  - pairwise, against the captured sha of every other committed subtask that
    has not landed.

  Each answer is clean, conflict (with the paths) or unavailable (any other
  exit, or git older than 2.38). merge-tree writes only unreachable objects:
  no ref, index or worktree changes. Measured 2026-10-07 on git 2.54.
- **Merge order**, advisory: the waiting subtasks in plan order (dependency
  order, then position). Each conflicting pair is marked "the later one
  rebases once the first lands".
- **Where.**
  - A terminal line.
  - A `landing-ready` record in the run ledger.
  - An append to `<main>/.agentic-plugins/runs/autopilot/landing/<macro-id>.jsonl`,
    beside the macro lock. The macro's subtask topic placed this file in the
    run directory. It moves here because deduplication has to outlive a run,
    and a stable path is what a watcher tails across relaunches.
- **Deduplication.** The key is (subtask id, engineer workflow id, captured
  sha).
  - A waiting subtask found unreported at run start is reported then.
  - A reported one is not repeated.
  - A new sha, such as a fix the owner pushed, is a new event.
- **Limits.** The event never pushes, opens a pull request or writes a ref.
  It adds no gate and no halt reason. The `awaiting-landing` halt lists the
  same facts per branch, with the overlap report and the order.

### Decision 8. Proposals: where worktree, lane and consensus advice appears

The six-field proposal (ADR-0029 §1) and the closed `next_step_kind` enum
stay. No proposal below needs a new kind. The driver never executes a
consensus round, a worktree or a lane change from a next step, so a new kind
would have no machine consumer: it would only add a value every reader must
refuse.

**1. Consensus on a conflict (L3): the `selected_next`.**
- **Trigger:** the synthesis verdict `conflict` in decide, critique and
  investigate (all three personas) and in orchestrator plan-verify. Never in
  compose, frame or refine, and never on `agreed`, `concerns`, `pass`,
  `resolved` or `regression`.
- **The durable proposal is a task file.** The verb writes the contested
  items, genericized as a peer prompt is, to
  `.agentic-plugins/state/<persona>/consensus/<workflow-id>.<run-id>.md` (for
  a macro, `.agentic-plugins/state/orchestrator/consensus/<macro-id>.<run-id>.md`),
  where `<run-id>` is the ensemble run whose synthesis was the conflict, in
  the workflow's own home (Decision 4, item 2), never in a lane's. There is
  one file per conflict. `runtime:consensus plan --task-file` reads it.
- **It is bound to its conflict.** A conflict gate (`decide-conflict`,
  `peer-conflict` or `plan-conflict`) records the run id of the synthesis
  that set it, `awaiting_owner_run_id`, in the write that sets the gate:
  `finish-verb --owner-gate-run-id` for a verb, `awaiting-owner-set
  --run-id` inside a `/<persona>:start` lifecycle, which sets its gates
  that way (`persona-pipeline/regions/start-phase-boundary.md:17-20`), and
  `plan-set --run-id` in orchestrator plan. It goes with the gate's other
  keys on a clear. Every write that sets a gate sets the key or deletes it:
  a gate set with no run id (an owner selection or a veto under
  `decide-conflict`, any other gate) deletes it, and since a gate may be
  set again over itself (`persona-pipeline/files/scripts/state.mjs:2943-2950`),
  a re-set that names another run, or none, retires the file of the run it
  replaces.
  A task
  file is current only while all of these hold: a conflict gate set on the
  workflow records a run id; the workflow's `ensemble_results` holds that
  run with the verdict `conflict`; and the file's name carries that run id.
  A run that publishes after another set the gate (a re-plan resumed late,
  a second session on the workflow) therefore never makes its file current:
  the gate names the run that set it. `decide-conflict` also marks an owner
  selection and an unresolved veto
  (`plugins/engineer/commands/decide.md:369-372`), which record no run id
  and write no file, and so never match. The key is new: CP ships it with
  the `peer-conflict` gate, readers first (Decision 4, item 3).
- **Every way a conflict gate leaves retires its files.** A retired file is
  renamed `<workflow-id>.<run-id>.resolved.md`, kept as evidence:
  - `awaiting-owner-clear` retires the file of the gate it clears, where
    today a clear removes only the gate's keys
    (`persona-pipeline/files/scripts/state.mjs:3047`). In the personas it
    is the only way a gate leaves: setting another gate over it is refused
    (`:2944-2949`);
  - a gate set again over itself retires the file of the run it no longer
    names (above);
  - `plan-set` retires every task file of the macro before it writes. A
    re-plan replaces the macro's gate without a clear: the previous plan's
    `plan-conflict` goes with it, and the new verdict sets the next gate
    (`plugins/orchestrator/scripts/state.mjs:3131-3137`).
- **No file is current before its own result.** The persona verbs record
  the ensemble result (`peer-runner settle`) before `finish-verb` sets the
  gate. Orchestrator plan sets its gate in `plan-set`'s write
  (`plugins/orchestrator/commands/plan.md:148-162`) before `ensemble-commit`
  records the run's result (`:211`), and writes the new task file after
  `plan-set`; until the gate's own run has its result and its file, nothing
  is current. An interrupted re-plan that also conflicted leaves a gate
  naming a run with no result or no file: the driver halts as usual, with
  no consensus proposal. A later gate of the same workflow, of any kind,
  therefore never meets a stale proposal.
- **The proposal:**
  - `selected_next`: owner decision, after a bounded consensus round;
  - `next_command`:
    `/runtime:consensus plan --task-file <absolute path of that file> --peers claude,codex --max-rounds 2`.
    The path is absolute because `consensus.mjs` resolves it against its
    working directory (`:2752`). The pointer in the phase note keeps the
    relative spelling;
  - `rejected_alternatives` includes "the owner decides now", with the reason
    for this case;
  - the owner then decides, with the consensus result as evidence.
- **Gates.**
  - decide keeps `decide-conflict`, and orchestrator plan keeps
    `plan-conflict`.
  - critique and investigate record a new gate, `peer-conflict` (heading
    `### Ensemble synthesis`, anchor `ensemble-synthesis`), in either mode,
    through `finish-verb --next-step-kind owner-decision --owner-gate peer-conflict --owner-gate-anchor ensemble-synthesis --owner-gate-run-id <run id>`.
    `awaiting-owner-clear --gate peer-conflict --resolution "<the owner's ruling>"`
    with the next step resolves it.
  - Without this gate, the interactive `finish-verb` would close the workflow
    (§Context). Other gateless owner decisions keep today's behaviour.
  - The gate is a pipeline gate, available to all three personas.
- **Never executed automatically.** An interactive session shows the
  proposal, and the owner runs it.
  - Under autopilot the driver halts as today: `awaiting-owner:decide-conflict`,
    `awaiting-owner:peer-conflict`, or `plan-unapproved` under `plan-conflict`.
  - Its halt record and `printHalt` carry a `consensus` entry in
    `proposals` (item 5).
  - The driver renders the command from closed parts only: the gate, the
    persona, the checked workflow or macro id, the run id the gate records
    (checked against the run-id alphabet) and the home it
    found that workflow in. It prints the command only when the task file
    is current by the rule above, which it judges from the frontmatter and
    the file's existence, never its content. No stored text becomes a
    command (R5).

**2. Lane advice (L4 at plan and approve): a line after the six fields.**
- Example:
  `- lane_advice: A and B are independent, C waits on both: /orchestrator:autopilot start --execute --macro <macro-id> --lanes 2`.
- **Computed each time** from `plan.subtasks[].blocked_by`: a critical-path
  simulation at 1 lane and at 2, bounded by the widest ready set, as the
  precedent's main session did by hand. It is shown when two lanes shorten
  the critical path, and otherwise omitted. Its command is shown only when
  shared creation is on (`state.mjs state-root`, Decision 6) and the
  macro's own path lies under the default state root, the admission
  conditions plan can check; otherwise the line says the cutover comes
  first (Decision 4, item 4).
- **The command names the macro.** It carries the macro's checked id as
  `--macro <id>`, as the relaunch command does (Decision 6): without it,
  `start` drives the macro active on, or referencing, the current branch
  (`plugins/orchestrator/adapters/claude/autopilot/observe.mjs:164-171`),
  which may be another macro.
- It is display only: not projected into `next_step`, never a stored field,
  never read by a machine.
- **Precedence in plan's single proposal:** conflict resolution (1 above)
  first, then approval (`/orchestrator:approve`), with the lane advice beside
  either. CP owns the conflict branch. WP owns the approval branch and the
  lane advice.
- **Shared numbers.** The planner pre-assigns, in the subtask topics, any
  number that two lanes could both take: ADR numbers, ports, section numbers.
  This is the owner's default; it answers the precedent's 73 edits.

**3. A worktree first (L4 at start and next): the `selected_next` of the
refusal.**
- **Where.** A dirty tree or another active workflow blocks the work: a
  persona start refuses a dirty tree before it bootstraps
  (`persona-pipeline/regions/start-bootstrap.md:118-133`, the clean-baseline
  refusal) and an active workflow that is not a start
  (`persona-pipeline/regions/start-resume.md:20-22`); `/orchestrator:next`
  refuses a dirty tree before it switches branches (`next.md:229-234`). There
  the proposal selects a worktree.
- **Only where the new worktree can find the macro.** For
  `/orchestrator:next` the worktree is proposed only when the macro lies
  under the default state root: after the cutover, every macro not created
  under `AGENTIC_STATE_BASE` naming its own checkout; before it, only a
  macro of the main checkout, in a repository with a shared root. A
  macro kept in a linked worktree's
  own home is in no other worktree's read set (Decision 1(a)), so
  `/orchestrator:next` run in a new worktree would not find it. There the
  refusal keeps its own options, and the proposal names the cutover
  (Decision 4, item 4) as what makes a second worktree usable.
- **The command is the runbook's**, rendered from a fixed template with
  values it resolved and checked, at `<parent>/<repo>-<slug>`, the path
  `runtime:worktree` uses (`plugins/runtime/scripts/worktree.mjs:383-386`):
  - `/orchestrator:next`, the subtask branch absent, with an `origin`
    remote: the fetch of Decision 5's Creation step 1, then
    `git worktree add --no-track -b <branch> <path> refs/remotes/origin/<baseline>`,
    the base next.md itself would use (`next.md:304-311`). The fetch comes
    first because next.md, run again in the new worktree, finds the branch
    and takes its switch path, which skips its own fetch (`next.md:301-302`).
    When that fetch fails, the command says so and uses the last fetched
    ref, next.md's rule;
  - `/orchestrator:next`, the subtask branch absent, with no `origin`
    remote: `git worktree add -b <branch> <path> refs/heads/<baseline>`, as
    next.md branches from the local integration branch then
    (`next.md:313-316`);
  - `/orchestrator:next`, the subtask branch present:
    `git worktree add <path> <branch>`;
  - a persona start, for new work on a new branch: `runtime:worktree
    plan`'s `git worktree add -b <branch> <path> <base>` (`worktree.mjs:203`).
    The planner serves only this case: it blocks with no command when the
    branch exists (`:180`, `:189-199`), sets no `--no-track`, and bases on
    `origin/main` by default (`:14`).

  The runbook then says to run the same command again inside the new
  worktree.
- Each refusal's existing options (next.md's commit, stash or revert; a
  persona start's clean, stash or accept) stay among the rejected
  alternatives, each with its reason.
- When the request belongs to the existing workflow, the ordinary resume
  stays the selection.
- These refusals come before any workflow is written, so nothing is
  projected into `next_step`. Under autopilot they do not arise: the driver
  halts `dirty-tree` before a serial dispatch, and a lane's dispatch runs in
  a fresh lane.

**4. Autopilot launch (L4).** Preview and start handle each trigger
separately, and the provenance and drift checks behind them:
- **Launched on the main checkout.** For a serial run, whose steps switch
  that checkout's branch, the driver proposes the home-worktree setup: the
  `git worktree add` and the version pins from the installed cache. This
  replaces the unconditional line at `cli.mjs:261`. With `--lanes 2` or more
  no step switches the driver's checkout, so a launch on main is allowed,
  but done and finalize run there and its checks read it (Decision 6,
  Policy): an owner's workflow, a foreign one or a checked-out commit on
  main halts the run at its next done and drains every lane. So the driver
  proposes the home-worktree setup for a lanes run too, as the checkout to
  launch from: one no one works in.
- **Plugins loaded from a directory marketplace.** Commands, skills and
  hooks load from the marketplace checkout wherever the driver runs, so the
  home-worktree setup does not shield a run from it. When a loaded plugin
  lies in a git worktree the owner works in (on the owner's machine, the
  main checkout), the preview and start say that a pull, a branch switch, a
  commit that changes a plugin directory there, or an uncommitted edit in
  one, halts the run at the next worker start (Content drift, below), and
  propose the remedy: point the marketplace at a snapshot worktree no run
  drives and no one updates (`git worktree add --detach <path> <commit>`),
  or leave that checkout's plugin directories alone for the run.
- **Plugin roots inside the repository.** The refusal and its provenance
  checks stay (`roots.mjs:149-157`, `driver.mjs:149-176`), rescoped by the
  next bullet (today `driver.mjs:157` compares with the driven checkout
  only, which with lanes is not what a step switches), now with the
  concrete setup: pins to the installed release caches, or to a snapshot
  worktree or clone that no run drives.
- **The provenance check covers every checkout whose branch a step of the
  run switches:** the driven checkout in a serial run; each lane with lanes,
  where the driver's own checkout is not switched. A plugin loaded from
  another worktree of the repository (the main checkout's directory
  marketplace, a snapshot worktree) passes this check, because no step
  switches that worktree's branch.
- **Content drift.** A step does not switch those worktrees, but the owner
  may change them. On a directory marketplace a pull, a branch switch, a
  commit or an edit in the marketplace checkout changes the commands,
  skills and hooks later workers load, while the plugin versions stay equal
  (Decision 4, item 3). A pinned script root kept in a snapshot worktree or
  clone (above) changes the scripts every runbook block runs when that
  checkout moves. Today the driver compares versions and paths only, of the
  loaded plugins (`driver.mjs:164-173`) and of the pinned roots (`driftOf`,
  `roots.mjs:160-170`). So it fingerprints the content of both:
  - for each loaded plugin path and each pinned root that lies in a git
    checkout: the tree id of that directory at the checkout's HEAD
    (`git rev-parse HEAD:<dir>`), and that the directory holds no
    uncommitted change, tracked or untracked (`git status --porcelain
    --untracked-files=all -- <dir>`). The pinned roots are fingerprinted at
    start, the loaded plugins at the first worker's start;
  - the pinned roots are checked again before each step, beside `driftOf`
    (`driver.mjs:388-389`), and the loaded plugins at each worker's start,
    beside the provenance check. A different tree id, or an uncommitted
    change, halts the run `version-drift`; at start it refuses the launch;
  - a root outside any git checkout (an installed release cache) keeps
    today's comparison of version and path.

  This applies to serial runs too.

**5. In autopilot reports.** The halt record, `printHalt` and the preview's
JSON report carry `proposals[]`, each `{kind, command, pointer}` with a
closed `kind`:
- `consensus`: item 1;
- `worktree`: the launch triggers of item 4, at preview and start;
- `lanes`: a serial run that halts while two or more subtasks could run
  side by side, recomputed from `plan.subtasks[].blocked_by` as in item 2,
  and only when the run would be admitted with lanes: the capability floor
  of Decision 6 holds, shared creation is on, the effective root is the
  default one, and the macro and its active children were found there
  (Decision 2). Its command is
  `/orchestrator:autopilot start --execute --macro <id> --lanes 2`, with the
  halted run's checked macro id (item 2).

Each entry is built from facts the driver has checked: identifiers against
its closed alphabets, paths it resolved itself, fixed templates. It is
display only, bounded, and never acted on by the driver.

## Consequences

**Positive**:

- Independent subtasks run at the same time: two lanes by default, each a
  pull request of its own, with the landing rules unchanged.
- The owner learns of each commit when it is made, not when the run runs out
  of work (C118). Each report says whether the branch merges cleanly with
  `main` and with the other waiting branches, and in which order to merge.
- One copy of every workflow per repository. The owner's main session sees
  the macro it controls, with nothing symlinked or copied.
- Parent writeback no longer depends on where it runs, and it checks the
  identity of the macro it writes to.
- A contested decision, finding or diagnosis stops with a ready consensus
  command instead of an open question. A contested critique no longer closes
  its workflow.
- Worktrees and lanes are proposed exactly where the owner had to ask for
  them.

**Negative**:

- "State is per worktree" becomes "state is per repository".
  `AGENTIC_STATE_BASE` keeps a checkout's new records in its own homes,
  except a dispatched child once shared creation is on. Its only other
  value, allowed once the switch is on, is the default root, which is all
  lanes accept.
- The interactive orchestrator commands take part in the run locks
  (Decision 4, item 5). A session that dies between a command's blocks
  leaves admission entries that block a run, and the owner's retry, until
  the owner releases them. The guard narrows the race between a check and
  its action; it does not close it.
- One active macro per integration branch per repository (Decision 1(a)):
  two macros on `main` can no longer run side by side from two checkouts.
  A pair that exists when RR arrives has to be resolved first (Decision 4,
  item 1).
- Git cannot prove which directory is the main checkout, so the operator
  attests it once, with checks for plain mistakes (Decision 1(a)). A
  repository whose main checkout keeps its git dir elsewhere fails them, or
  has no shared root at all: it gets no lanes and keeps creating records
  per checkout.
- A one-time operator cutover: every session of the repository closed on
  both hosts, a release tuple installed and verified on both, any macro in a
  linked worktree moved, with every child a linked worktree holds of a
  shared macro, and shared creation switched on. Until the switch,
  records are created per checkout as today, so installing on one host
  first splits nothing. Getting the move wrong can still split a workflow.
  The manifest, the rename-only rule, the writers' locks and the ambiguity
  error make a split visible and recoverable; they do not make it
  impossible.
- Rollback ends when lanes first run. After that, problems are repaired
  forward.
- N lanes spend the five-hour window about N times as fast. The throttle
  gates new lanes, not steps already running.
- The seven-day window is reported, not gated (the owner's reading): lanes
  can run a week's allowance down faster, and only a `rejected` status stops
  new lanes there. The seven-day warning appeared in 13 of 39 measured runs.
  A worker whose events name only the seven-day window leaves the five-hour
  status unknown; its five-hour utilization alone then decides (Decision 6,
  rule 3, the owner's decision of 2026-10-08).
- Each lane is a full checkout on disk until its subtask lands.
- Lanes can each pass on their own and break once merged. The overlap check
  sees textual conflicts only; the review is what catches semantic ones.
- More contract surface: three variables, a shared-creation switch, a
  linkage key, a gate, admission entries, a landing log, lane intents,
  open-run records, a cutover manifest, and the proposals in five places.
- On a directory marketplace, the marketplace checkout's plugin directories
  are frozen for the length of every run, serial runs included (Decision 8,
  item 4): a pull, a branch switch or a commit there that changes a plugin
  directory halts the run at the next worker start (`version-drift`), and
  an uncommitted change in one refuses the launch or halts the run. On the
  owner's machine that checkout is the main checkout, where the owner
  works, so working there on a plugin stops every run until the marketplace
  is pointed at a snapshot worktree no one updates. The cutover also waits
  until that checkout carries the tuple.

**Neutral**:

- Serial runs (`--lanes` absent or 1) keep their policy. What they gain is
  not lane-specific: the landing-ready event, the admission entries and
  worker token, the content drift check, and the dead-run cleanup
  (Decision 6).
- Codex stays manual (ADR-0063 D9). Installed at the tuple, it reads the
  shared records; it creates them there once shared creation is on.
- Runtime's tiers and executor guard are unchanged.

## Alternatives Considered

**A local integration branch with a merge-conflict gate** (worktree-parallel
W4, W7). The driver would merge each finished lane into
`integration/<macro-id>` and halt on a conflict. Rejected by L1: under
ADR-0062 a local merge completes nothing, and a merge conflict there is a
landing-time problem the owner's review sees anyway. The read-only overlap
check gives the same early warning with no ref written.

**Symlinking state into each lane (A-lite).** Measured in the design's W3
experiment and in the precedent. Rejected:
- the symlink is a file, so the `state/` ignore rule misses it, and in the
  precedent a whole-`state` symlink failed the clean check;
- linking only some homes leaves the rest split;
- it works only for lanes the driver made, and not for the owner's own
  worktrees.

**Copying state into a lane and syncing it back.** Rejected: two writable
copies, which is the failure Decision 4 exists to prevent.

**A ledger record as the proof of lane ownership.** Rejected: a crash
between `git worktree add` and the record leaves an unowned lane. The git
lock reason is written by the same operation that creates the worktree.

**Claude Code's `-w <name>` worktrees.** Rejected: the path
(`.claude/worktrees/<name>`) and the branch (`worktree-<name>`) are fixed,
and do not fit `subtasks[].branch` (Claude Code 2.1.281, observed in
worktree-parallel §2.5).

**Subagents with `isolation: worktree`.** Rejected: no `SubagentStop`
writeback and a conductor context that accumulates, two of the reasons
ADR-0063 rejected a subagent conductor; and worktrees deleted when unchanged,
with nobody able to attach (worktree-parallel §2.5).

**A new `next_step_kind` (`consensus`, `worktree`).** Rejected: no machine
consumer would act on it, since the driver may not run either, and every
reader of the closed enum would have to refuse one more value.

**Running consensus automatically under autopilot.** Rejected by L3. A
contested point is a judgment (R2), and a consensus round costs peer runs
the owner has not approved.

**Committed lanes hold capacity.** Rejected (Decision 6): a waiting lane
spends nothing, and holding a slot would stop a two-lane run after two
commits.

**Throttle by pausing running lanes.** Rejected: it idles work already paid
for, and the owner's default gates new lanes only.

**Creating under the shared root from the SR release on.** Rejected
(Decision 4, item 3): the two hosts are upgraded independently (a Codex
install moves only with its pin, ADR-0061), and an older persona in a linked
worktree never looks under the default state root, so it would start a
second workflow for a branch beside one the newer host created there. SR
ships the readers with creation unchanged, and a repository-scoped switch,
turned on once both hosts are verified, starts shared creation. A later
release that flipped the default would have the same flaw on any machine
that had not installed it on both hosts.

**A test of the default state root on every read.** Rejected (Decision
1(a)): in a repository whose main checkout keeps its git dir elsewhere, the
git dir's parent passes the name test and answers the questions a checkout
answers about itself as a real main checkout does (`git rev-parse
--show-toplevel` names it, with the same common dir, measured), and git
records no main worktree path to compare with. A look at its files tells
the plain case apart, but it is a heuristic (a file named as a tracked one
passes it), and every reader in every plugin would repeat it at each lookup
(runtime and attention compute the root by copy, ADR-0010 §5). Reads there
find nothing anyway, since nothing is created there; what needs the
judgment is shared creation. So the operator attests the main checkout
once, when the switch is turned on, the same checks catching plain
mistakes, and lanes, which need the switch, follow.

**Rollback destinations from `repo_root` for every record.** Rejected
(Decision 4, item 4; it is read only for a record created after the
switch):
`repo_root` records where a record was created, and a record moved since
keeps it. This macro, moved by hand into the autopilot home, records the
main checkout, so a rollback by `repo_root` would leave it in the main
checkout and send its child back to the home, a split the old tuple cannot
serve. The cutover's manifests say where each record lived.

**`AGENTIC_STATE_ROOT`.** Rejected (Decision 2).

**An override that may name any worktree of the repository.** Rejected
(Decision 2): a record created there is found only by sessions that carry
the same value, so a session of the same checkout without it would create a
second workflow for the branch. The two values the read set already covers
are the only safe ones (only the checkout's own toplevel while shared
creation is off).

**A checkout-scoped marker in place of the variable** (a file in the
checkout that names its state root). Every session of a checkout would
agree by construction, which is as sound as the read-set rule. Not chosen:
it replaces the override variable the owner's W3 default names. It stays
open to the owner at review.

**One lock entry listing every worker group (`workers[]`).** Rejected
(Decision 6): today's reader judges an entry by its one `worker`, and once
that group ended it would delete the entry while another group still ran.
One entry per group keeps every reader right.

**Pruning a lost lane's metadata from the driver.** Rejected (Decision 5,
row 1): `git worktree prune` has no path selector, so a dry run does not
bound what the prune that follows removes.

**A process group as a worker's proof of admission.** Rejected
(Decision 4, item 5): a worker's descendants can leave its group. A per-run
secret proves it.

**Admission entries that expire after a lease.** Rejected (Decision 4,
item 5): expiry admits a competing writer while the admitted command, paused
or slow, can still switch the branch or write the macro. An entry stays
until it is released, each guarded action checks its own admission id
first, and the owner releases an abandoned one.

**A retry that replaces its own earlier entry.** Rejected (Decision 4,
item 5): a session that died and one still inside a step look alike (same
command, checkout and host), and `/orchestrator:next`'s first verb runs
under no check, so a replacing retry could switch the branch under it.
Routine refusals leave no entry instead: the join comes after the read-only
checks, and every later exit releases.

**Admission entries keyed by macro, checkout and command.** Rejected
(Decision 4, item 5): a release could not say which entry it drops, and a
session resumed after the owner released its entry and re-ran the command
would pass the check on the new entry. A random admission id per join,
passed to every check and to the release, ties each guarded action to its
own admission.

**A dead run's lock entries as its recovery pointer.** Rejected
(Decision 6, Locks): an older driver, and any consumer that reuses its
cleanup, deletes entries judged gone. The open-run record, in a directory no
lock consumer lists, is the pointer.

**A removal intent alone as the proof of an unlocked lane.** Rejected
(Decision 5): a removal that succeeded just before a crash leaves an open
intent for a path that may since hold another worktree. The lane id written
into the lane at creation tells them apart.

**Gating lanes on version numbers.** Rejected: on a directory marketplace the
loaded text and the pinned scripts can differ in version (ADR-0063 S0, S8).
The driver probes capabilities instead, as S8 does.
